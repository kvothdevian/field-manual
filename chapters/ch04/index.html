Fixing the same thing twice is a configuration problem

Here is the quiet tragedy of an unconfigured agent: every session starts blank. The loop has no memory of yesterday except what you leave on disk. So when the agent uses the wrong test command, edits a generated file, or writes commit messages in a style you hate, and you correct it in chat, that correction dies with the session. Tomorrow morning it makes the same mistake again, and you pay for it again, forever.

Every serious harness offers three layers of standing configuration, and the distinction between them is the whole skill:

  • Memory files — prose loaded into context automatically at session start. They persuade. The model reads them like advice from a colleague, and can ignore them like advice too.
  • Skills / playbooks — instruction files kept out of context until a matching task appears, then loaded on demand. Economy: capability without rent.
  • Guardrails — hooks, permission rules, plan modes. Code that runs before or after the model acts, regardless of what the model believes. Enforcement.

The leverage is compounding. A fix typed into chat pays once; the same fix written into a memory file pays every future session, across every project that inherits it. Configuration is the only part of your agent setup that grows more valuable the longer you use it — which is why this chapter comes before the fancy patterns.

§2

Watch instructions load: the nested-files simulator

Instruction files nest. There is usually a global one for your whole machine, one per repository root, and optionally deeper ones per package or subfolder. When the agent works on a file, most harnesses walk from that file's folder upward, loading every instruction file it passes — and when two files disagree about the same topic, the nearest file wins. Flip the toggles below to create or delete files, switch which file the agent is editing, and watch exactly what enters its context.

Three lessons fall out of that panel. First, global defaults are the floor: personal preferences live far from any repo and apply everywhere. Second, nearest wins ties: the moment a package declares its own testing rule, the identical topic in the root file is dead letters for anyone working down there — which is why "but my root file says so" is not a debugging strategy. Third, siblings never leak: the lib package's purity rules never touch app code, because the loader walks up, not sideways. This nesting-and-precedence behavior is specified, not accidental, as the receipts below show.

tip

Start with five lines, grow on evidence. Do not generate a 300-line constitution on day one — long memory files dilute the short ones and cost context every session. Write five lines today. Then apply the promotion rule: the moment you correct the agent about the same thing twice, promote that correction into the file. Your memory file becomes a fossil record of your actual friction, not your imagined one. The same grow-on-evidence bar covers npm-installed plugins, which execute their code at startup before you see anything — treat every install like adding an npm dependency to your own app and vet it first; chapter 2 owns the full supply-chain warning.

warning

Config rot is real and actively harmful. A stale instruction doesn't just stop helping — it misleads: last year's "always use library X" turns every fresh session into a fight against your own file. Date every rule ("adopted 2026-08, because Y"), review the file quarterly, and delete anything you can't explain the reason for. An instruction file nobody rereads is a liability wearing a productivity costume.

§3

The names you will meet

AGENTS.md is the cross-harness attempt at one standard: an open, tool-agnostic instruction-file format stewarded under the Linux Foundation, with nested files resolving nearest-wins exactly as the simulator showed, adopted by Codex, Cursor, opencode, GitHub Copilot coding agent and Gemini CLI. Write one and several harnesses read it unmodified. Claude Code centers its own family instead: CLAUDE.md files arranged in a managed → user → project → local hierarchy, with @-imports, path-scoped rules, and an auto-memory index called MEMORY.md that reloads every session under a hard load cap of roughly 200 lines / 25 KB — overflow stays on disk unread, which is itself an argument for short files. And Claude Code's documentation states this chapter's spine better than we could: memory is context, not enforcement — use hooks and settings to actually block anything.

Skills: knowledge that loads only when needed

A skill is a SKILL.md playbook — "how we deploy," "how we add a pricing row." Its genius is progressive disclosure: every session pays only for the skill's name and description (a line or two), while the full body loads only when the task matches. A frontmatter flag such as disable-model-invocation goes further, keeping a side-effecting skill entirely out of the model's reach until you summon it explicitly. Compare that with pasting the same procedure into your memory file, where it taxes every session whether or not it is relevant. Playbooks you want always-available go in memory; procedures you want available-on-demand become skills.

Hooks and permissions: guardrails the model cannot argue with

Prose persuades; exit codes compel. Hooks run your shell commands at lifecycle points — before a tool executes, after each edit lands, when a session ends — and a hook that exits with code 2 blocks the underlying action outright. The model cannot negotiate with an exit code, which is exactly the point: use hooks to auto-run lint after edits, or to enforce rules your memory file keeps getting talked past. One honest caveat from the docs themselves: a hook's if filter fails open — break the filter and actions pass through — so put hard denies in permission rules rather than trusting filter chains.

Permission rules evaluate in a strict order: deny beats ask beats allow. A deny rule like Read(./.env) makes secret files unreadable no matter how convincingly the model justifies the read; a glob like Bash(git push *) forces every push to stop for a human. Set the denies first — they are the floor that survives even a bad day.

Two modes worth flipping deliberately

One flip earns its keep specifically during configuration work: turn opencode's language-server integration on, and live compiler diagnostics immediately confirm whether the build commands and generated paths your freshly written rules point at actually exist. The full feature tour lived in chapter 2. Similarly, plan mode lets the agent draft a full approach read-only before any disk write, and git worktrees give each parallel session an isolated checkout — two agents, two branches, zero trampled edits.

§4

Where this lands in your build

Build 1 — the agent-cost-compass — gets its own AGENTS.md at Milestone 2, alongside the calculator core, and ours is this chapter's living example. It opens as five lines, seeded directly from the build spec's known pitfalls:

# AGENTS.md — agent-cost-compass
- $0-only: flag any paid tier suggestion with its cost
- every price row carries an as-of date + source URL — staleness kills this product
- verify with: node scripts/check-data.mjs (must pass before any commit)
- conventional commits; human gate before anything publishes

By Milestone 4 it has grown — but only via the promotion rule, one line per repeated mistake, each dated. The build log records what got added and why, which doubles as the quarterly-review checklist the config-rot warning demands.

§6

Try it yourself

  1. Exact-click checkpoint: write your first AGENTS.md tonight. Open your editor at the root of any project you care about. Create a file named exactly AGENTS.md. Paste this template and fill the five placeholders:
# AGENTS.md — <project name>
what this is: <one sentence a stranger could act on>

commands:
- install: <exact command>
- test: <exact command>

rules (dated, pruned):
- <a correction you have made at least once>

last reviewed: 2026-08-<day> by <your name>
  1. Verify it loads. Restart your harness inside that folder and ask: "list the standing instructions you are running under." If it cannot echo your rules back, check the filename and location — the echo trick is how you audit any harness's memory loading, including the nesting behavior from the simulator above.
  2. Break it on purpose, ship-sized. Add one contradictory rule to your new file (e.g., "use tabs" vs your real style), predict which instruction wins when both sit in context, then ask the agent to write a small function and grade the result against your prediction. Afterwards, delete the lie and promote your most-repeated real correction into the rules list — dated. That file now earns its keep.
§7

Self-check

Your AGENTS.md says "never edit generated files," yet the agent keeps editing them. Which layer do you reach for, and why?

Enforcement, not context: a permission deny rule or a PreToolUse-style hook. As the docs put it, memory is context, not enforcement — prose can be outweighed by a strong local signal mid-task, while a deny rule or exit-code-2 hook physically blocks the write.

You work in packages/app. Both monorepo/AGENTS.md and packages/app/AGENTS.md define a test command. Which fires — and what happens to the other?

The app-level command fires; nearest wins ties. The root rule stays loaded but is overridden on that topic for files under packages/app — it would only fire again if the nearer file were deleted or stopped claiming the topic. Sibling packages' files never load at all.

Why does a five-line memory file beat a 200-line one, when a big procedure you sometimes need belongs in a skill instead?

Memory loads every session, so every line is a permanent tax — and caps like Claude Code's ~200-line MEMORY.md load limit mean overflow silently goes unread anyway. Skills invert the economics: only the description persists, the body loads on demand, and flags like disable-model-invocation can keep a skill out of context entirely until invoked.

§8

Beyond this build

Naming differs; anatomy doesn't. Every harness implements the same three layers under different labels. The AGENTS.md standard is read natively by Codex, Cursor, Copilot coding agent, Gemini CLI and opencode, so it is the best default for portable projects. Claude Code prefers its CLAUDE.md family — managed, user, project, local tiers plus the MEMORY.md auto-memory index — though skills and permission concepts map almost one-to-one onto the generic layers above. Gemini CLI also honors its own GEMINI.md at the equivalent spots. Learn the layers once and each tool's naming becomes trivia, not relearning.

Monorepos are where nesting earns its keep. Shared commands and commit conventions belong at the repo root; per-package quirks (test runner, generated-code bans, purity rules) belong next to the code they govern. If you find yourself writing "except in packages/lib" at the root, that sentence wants to be a nested file instead — the loader already knows how to scope it.

When configuration becomes cargo cult. Symptoms: a memory file copied from someone else's repo that no one has reread; rules referencing tools you no longer use; a "sacred" conventions file that contradicts what the team actually does. The failure is worse than having no config, because stale instructions actively steer every session wrong. Antidotes: date every rule, prune on a calendar, and apply one brutal test — if you cannot say why a rule exists, delete it. Configuration should be a fossil record of real friction, and fossils stop being evidence when they outnumber the living.
