Chapter 14 · Security & secrets

After this chapter you can name the three ingredients behind most agent exploits, check your own setup against them tonight, and lock the three doors that matter: secrets, untrusted content, and every way out.

facts checked as of 2026-08-26 · incident dates ride on each receipt

Agents earn their keep by combining abilities no earlier tool combined: they read whatever the project contains, act on the machine, and reach the network when a task demands it. Attackers read the same capability list upside down. Agent exploits almost always assemble from the same three ingredients — the shape most exploits share — and in June 2025 Simon Willison gave the combination its lasting name: the lethal trifecta. Private data, untrusted content, and an exfiltration channel — an agent holding all three is exploitable, and guardrails reduce the risk without closing it.

The legs deserve precise definitions, because sloppy ones ruin the audit:

  • Private data in reach. Anything whose escape costs you — API keys in .env, SSH credentials, session cookies, customer rows, unreleased plans. Reach means reachable by tools the agent may call, not what you intended to show it.
  • Untrusted content. Any incoming bytes an outsider helped write — web pages, issue comments, package READMEs, emails, tool output. The model cannot reliably separate commands from data, so every fetched page is a stranger whispering instructions.
  • A way out. Any channel to elsewhere — sending email, firing an HTTP POST, pushing to a public branch, writing into a synced folder. Exfiltration rarely needs sophistication. It needs permission.

Remove any single leg and the machine stops. Secrets with nowhere to go are just files; an exit with nothing sensitive behind it leaks boredom; a steerable agent holding neither is noise. That is a structural claim, not an aspiration — which is what makes it auditable. You are not improvising this alone, either: OWASP's GenAI project maintains a Top 10 for LLM applications, refreshed from a 2025 edition toward a newer 2026 edition with agentic-security initiatives underway, and prompt injection ranks near the top of every edition.

Three real machines, disassembled

Case A, in full. In September 2025 researchers at Koi Security documented the first malicious MCP server found in the wild: an npm package impersonating the official Postmark email server. From version 1.0.16 onward it silently added the attacker's address as a BCC on every email sent through it — password resets, invoices, private threads — while collecting roughly 1,500 downloads a week. Applying Chapter 07's corroboration pattern before printing any of this as fact: Snyk's independent analysis matched the indicators of compromise, and Postmark itself warned customers.

Case B, in full. About four weeks earlier, the nx build-tool compromise drew the same shape in harder lines. Trojanized packages swept developers' machines for .env files, SSH keys and wallet seeds — and, finding locally installed AI coding CLIs, invoked them with --dangerously-skip-permissions, --yolo and --trust-all-tools so the guardrails stepped aside first. Socket documented it as the first weaponization of AI CLIs in the wild; Wiz's aftermath analysis found roughly half of affected machines had an AI CLI installed, and measured how often guardrails refused when the flags were absent. The official GitHub advisory, GHSA-cxm3-wv7p-598c, anchors the timeline.

Set the two side by side and the uncomfortable commonality appears: neither headline attack was prompt injection. Both arrived as dependencies you chose to install, needed only private data + an exit, and let attacker-authored code stand in for the manipulation leg. The injection case — C — remains the everyday hazard, but the supply chain proved the bloodier courier. Hold that thought while locking doors.

Locking the three doors

The defense is almost disappointingly mechanical: starve any one leg and every attack above collapses. Three doors, three locks.

Door 1 — secrets. Live credentials belong in gitignored .env files, mirrored in repos only by placeholder-filled .env.example, and kept off the agent's readable surface wherever your harness allows. Never paste a real key into a chat: anything in context can leave in any later session's output.

Door 2 — untrusted content. Treat everything the agent fetches as testimony, never as orders. When a fetched page "reports" something alarming, make the agent quote it verbatim with its URL and verify before acting. Grant network-fetch tools narrowly, or not at all.

Door 3 — exits. Enumerate every channel outward — email, POST, pushes to public remotes — and give each a gate. Unused MCP tools get denied outright; used ones get asked-about.

Mainstream harnesses express this as a permission ladder evaluated in a fixed order: deny beats ask beats allow. Deny rules take path-scoped forms like Read(./.env) and glob shapes like Bash(git push *); managed-settings files enforce them independently of whatever the model decides. The official documentation ships paste-ready exclude-secrets rule sets — and documents their coverage precisely: a Read(./.env) deny reaches past the Read tool into Bash file-read commands such as cat, head, tail and sed; the surviving documented bypass class is an arbitrary subprocess opening the same bytes itself — node -e, python -c — so gate command execution too. Deny lists raise the floor dramatically. They are not walls.

warning · cross-ref ch04

Chapter 04 armed you with hooks as lifecycle enforcers. Their fine print matters here: a hook's if filter fails open — when the filter errors or mismatches, the action proceeds. Hard denials belong in permission rules, which fail closed by evaluation order. Keep hooks for observation, linting and soft nudges.

tip

Read what you allow-list like it's a contract clause. An allow rule is standing consent — it speaks for you in every future session, including the tired ones where a request looks almost right. Wildcard entries sign away more than they appear to. Schedule the re-read.

warning

The convenience-flag family — --dangerously-skip-permissions, --yolo, --trust-all-tools — is the actual attack surface. s1ngularity's payload didn't defeat anyone's guardrails; it invoked the CLIs with those flags, and the guardrails stood down, because a human had once declared prompts unwelcome. Skip-permissions belongs exclusively inside disposable sandboxes.

Try it yourself

  1. Run the trifecta audit tonight. From each project root, list secret-bearing files (PowerShell: Get-ChildItem -Recurse -Force -Filter ".env*"; macOS/Linux: find . -name ".env*"). Then inventory installed AI CLIs and check their configs for skip-permission flags. Finish with a three-line verdict per project: which legs are live?
  2. Paste the deny rule. Open code.claude.com/docs/en/permissions, copy the exclude-secrets deny block into your project's .claude/settings.json (create the file if absent), restart a session, and ask the agent to read .env — watch the refusal happen. opencode users: the same effect via permission deny rules in config.
  3. Threat-model one side project. Draw three columns — private in reach, untrusted inbound, channels out — fill each with real names from that project, then close the cheapest gap before sleeping (usually: deny one unused MCP tool).

Self-check

Name the trifecta legs — and why removing any one collapses the exploit.

Private data in reach, untrusted content flowing in, a channel out. Data with nowhere to go stays put; an exit with nothing sensitive behind it leaks nothing; a steerable agent holding neither steals nothing. The chain has no redundant links.

Why did postmark-mcp need no prompt injection?

The attacker authored the tool itself. Supply-chain malware replaces the untrusted-content leg with attacker-written code, so private-data-plus-exit sufficed — which is why dependency hygiene sits beside prompt-injection defense, not after it.

Where do hard denies belong, and why not in hooks?

In permission rules, which evaluate deny before ask before allow and so fail closed. Hook if filters fail open — an error or mismatch lets the action through — so hooks suit observation and soft nudges, not last-line denial.

Beyond this build

Supply-chain hygiene rituals. Pin versions and commit lockfiles so a surprise bump is visible. Quarantine every new npm package or MCP server: read what it claims, check the repo's age and maintainers, search it against advisories before it touches a real project. Remember the Ch 02 footnote that npm plugins execute code at startup — same ritual applies. Fewer installed tools means a smaller surface, and a quarterly re-read of your allow-lists keeps contract clauses current.

Reporting vulnerabilities. If you find a malicious package or a backdoored server: report through the registry's abuse channel, open or feed a GitHub security advisory against the impersonated project, notify the impersonated vendor, and write up indicators so the next searcher finds them. postmark-mcp died quickly because researchers published IOCs within a day — disclosure speed is part of the defense.

Threat-model your own side projects. The trifecta does not check how serious a repository is; it checks what your laptop holds. Weekend toys share a disk with production SSH keys and browser sessions, so they get the same three questions and the same three locks. Cheap insurance, paid in minutes — and the habit generalizes to every agent you will ever configure.
