Briefing · 5 min · what varies and what doesn't

i.Same loop, different leashes

Session 01 taught the machine: model, harness, loop. Here is the part that matters when choosing between harnesses — the loop is identical everywhere; the leash differs. Every serious harness reads files, edits them, and runs commands in a loop toward your goal. What actually varies, and what your scorecard will measure, is four things: which tools are exposed and how (opencode's minimal core versus Gemini's search-grounded kit), where the approval gate sits between proposal and execution, how much context survives between sessions (memory files, checkpointing, compaction), and the price of entry — license, auth wall, and what $0 actually buys.

That framing kills most hype comparisons. Star counts, model names, and editor integrations are fashion; the four leash dimensions decide your daily experience. A harness with aggressive auto-approval feels fast until it edits the wrong file. One with a generous free tier but amnesiac sessions feels cheap until you re-explain the repo every morning. The derby below forces each runner onto the same four dimensions with the same task, so differences you feel are differences that exist.

Take context survival seriously — it is the dimension beginners undervalue most. A session's memory has three fates: it persists (memory files like AGENTS.md or GEMINI.md that every future session reads), it checkpoints (Gemini's save-and-resume for complex sessions), or it compacts (long transcripts summarized to fit, with details lost). opencode leans on memory files plus subagents that keep the main context clean; Claude Code builds auto-memory as it works; Gemini checkpoints explicitly. When a harness "forgets" your repo conventions mid-week, this is the mechanism that failed — and the fix is always the same shape: write it down in a file the harness reads, don't re-explain it in chat.

The four runners in this session's derby: opencode (your default — MIT-licensed, terminal-first, 75+ providers, skills and plan/build agents), Claude Code (Anthropic's proprietary engine across terminal, IDE, desktop and web — subscription or Console account required), Codex CLI (OpenAI's Apache-2.0 Rust core spanning CLI, IDE, app and web cloud), and Gemini CLI (Google's Apache-2.0 terminal agent with the largest gratis allowance: 60 requests a minute, 1,000 a day on personal OAuth). Same task, same scorecard, your data.

Four harnesses, four answers to "where does the human sit": a switch, a script, a territory, a policy.

iii.The derby · 40 min · fixed task

One task, run everywhere you can reach: make the failing test pass without touching any other file. The opencode run below is executed and condensed from a real log (2026-09-03) — including the part where the loop stalled and needed a nudge, because that is normal and you should see it here first, not alone at midnight.

1.Build the derby repo

Goal: two files, one failing test, one commit — a task small enough that harness behavior, not task difficulty, explains the differences.

mkdir harness-derby cd harness-derby git init -q git config user.name "learner" git config user.email "learner@example.com"

Create total.js with a planted off-by-one bug, and total.test.js using only Node's built-in runner — no dependencies to install, ever:

total.js: function total(items) { let sum = 0; for (const n of items) { sum += n; } return sum + 1; } module.exports = { total }; total.test.js: const test = require('node:test'); const assert = require('node:assert/strict'); const { total } = require('./total.js'); test('sums a list', () => { assert.equal(total([1, 2, 3]), 6); });
git add -A git commit -qm derby-start node --test total.test.js
✓ Verify
  • The test fails with 7 !== 6 — the bug is real and the proof runs with zero installs
  • git log --oneline shows one commit

2.Run it on opencode — and watch it stall

Goal: a complete executed run on your default harness, stall included. Write the stopping condition first — one sentence on paper, the stopping line, as always: test green, no other files touched.

Make the failing test pass without touching any other file. Run node --test total.test.js to prove it.

The loop stalled: diagnosis done, fix never applied. ◆ nudge · "Continue: apply the one-line fix and re-run the test to green." ◆ run 2 · edit total.js → +1 −1 (return sum + 1 → return sum) ◆ run 2 · ran test → ✔ pass 1 · fail 0 · diff: 1 file changed Condensed from the real log, 2026-09-03. Two lessons for the price of one: loops stall after diagnosis (nudging with "continue" is normal operation, not failure), and keep logging artifacts out of the repo — the first run wasted a read on the author's own log file.
⚠ If stuck

Your run stalls the same way? Say Continue with the next concrete action named. Vague nudges ("keep going") restart the wandering; specific ones ("apply the one-line fix and re-run") finish it.

Read the card, not the marketing. The columns that predict your future: needed a nudge (stall rate is the real tax), proof habit (did it verify unprompted?), and diff discipline (one file, or a helpful "cleanup" you didn't ask for?). A harness that finishes fast but touches three files is slower than it looks — review time counts.

Read the executed opencode row as the worked example. Two runs looks worse than one — until you price what each column means. The stall cost one sentence of nudging and zero diff damage, because the stopping line ("test green, no other files touched") held the first run to reads and a test execution. The proof habit column is the strongest signal on the card: this runner verified before and after the fix without being asked twice. And diff discipline (+1 −1, one file) is what made review take eleven seconds. When you fill other runners' rows, score them against exactly this: does the loop verify unprompted, does the diff stay inside the goal, and when it stalls, does it stall safely?

5.Pick your default — in writing

Goal: a decision rule you can reuse, not a favorite. Write one sentence: "I default to ___ because ___, and I switch to ___ when ___."

A working example from this book's stance: default opencode (free binary, every model, plan/build gates), switch to Gemini CLI for quota-heavy bulk work inside its 1,000-request day, reach for Claude Code when the budget allows and memory across sessions matters. Your sentence will differ — the point is that it exists before the next session, not after the next hype cycle.
