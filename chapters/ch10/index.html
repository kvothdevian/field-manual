Chapter 10 · Debugging when it breaks

facts checked as of 2026-08-26

Promise: after this chapter you can drive a disciplined debug — reproduce, hypothesize, bisect — instead of watching an agent thrash, and you know exactly when to pull the plug.

Breakage is not the exception in agentic work; it is Tuesday. The difference between a beginner and a practitioner is not that practitioners break less — it is that their next move is scripted. Beginner: paste the failure into the agent, receive a confident edit, repeat until either the bug dies or the diff becomes landfill. Practitioner: capture the symptom, force it into a proof, cut the search space in half, and reach for the escape hatches early. This chapter drills that script until it is muscle memory.

Reproduce before you explain

A bug you cannot summon on demand is a bug you cannot prove dead. Before any theory, before any edit, get a repro recipe: the exact input, the exact click or command, the expected result versus the actual one, written down. Official best-practices documentation for leading harnesses encodes this as the first discipline of debugging with an agent — reproduce the issue, and fix the root cause, not the symptom. Those are two rules, not one. Suppressing an error (wrapping the crash site in a silent catch, returning a default value so the page renders) makes the pain stop while the disease spreads.

The upgrade path from repro is a failing test: encode the recipe as an assertion that goes red today and must go green tomorrow. This does three jobs at once. It converts a vague complaint into a pass/fail switch. It stops the agent — or you — from declaring victory prematurely, because the proof is executable. And it hands every later tool, including bisection below, the automatic good/bad oracle they need. Agents will not do this unprompted; demanding the failing test is your move.

A bug you cannot summon on demand is a bug you cannot prove dead.

tip

Paste the exact error text, never a paraphrase. Not "there's a type error somewhere in checkout" — the full message, the file, the line number, the stack. Models route on specifics; a paraphrase sends them hunting in the wrong county. Same rule for your own notes: the exact string is searchable, greppable, and comparable after the next attempt.

Escape hatches, straight from the docs

Runaway correction loops are so predictable that harness manuals document the exits officially. Know them by name:

  • Rewind to a checkpoint. Sessions checkpoint as they go; /rewind in Claude Code restores conversation and code to an earlier point, so a bad direction costs minutes, not an evening.
  • Clear after two failed corrections. Official guidance draws a bright line: when corrections keep missing, stop correcting. Start a fresh session with clean context and lead with the exact error text.
  • Hook-enforced iteration caps. Hooks are deterministic guardrails you write yourself (the ch04 pattern), so a custom Stop hook can count correction rounds and cut a spinning loop off at a fixed cap — but no harness ships an anti-thrash mechanism by default: stock Stop-hook behavior is verification gating, checking the work passes before the turn ends. Caps are a pattern you install, not a stock mechanism.

Beneath the hatches sits environment quality — Ronacher's advice from a year of agentic coding, and it holds: keep everything logged to one file you can actually read afterwards; keep the feedback loop fast enough to rerun after every change; prefer commands that fail loudly; and when context compaction hits a long session, abort and restart rather than nursing a degraded one. A slow loop and a murky log are how two-minute bugs become two-hour sessions.

Bisect: halving beats walking

Oldest trick in the book, and it survives agents perfectly. When you have an ordered history — commits, config edits, deployed changes — and something flipped from working to broken somewhere along it, do not walk the list. Test the middle item. Working? The culprit is in the back half. Broken? The front half. Either way you just deleted half the suspects with one test. Sixteen candidates fall to four tests, because ⌈log₂ 16⌉ = 4; a linear walk drags through up to fifteen tests and averages more than eight. Git productized the loop decades ago: git bisect checks out midpoints, takes your good/bad verdicts, and names the first bad commit — and git bisect run hands your test script to the loop so git plays both sides and you never click anything.

Feel the race before you memorize the math. Sixteen commits below, one of them introduces a bug — re-randomized every reset. Pick a strategy, then click commits to test them. Par is 4.

Reading the wreckage

When the failure lives in a browser, the crime scene photographs itself — if someone remembers to shoot. Playwright's trace viewer records every action on a timeline with Errors, Console, and Network tabs attached, so a post-failure review is scrolling a film, not guessing from memory; teams commonly wire traces to fire on the first retry in CI so flaky failures leave evidence behind automatically. Driving the same browser through an MCP server adds live forensics: console messages arrive with source-mapped stacks and network inspection rides along, which means the agent can quote the failing request instead of describing it from vibes.

Two habits make any of these artifacts legible. Read a stack trace backward: the top frame is where the error was noticed, the deepest frames are where it was born — start at the birth, not the notice. And keep Ronacher's one-file rule: when every session logs to one place, the question "what did we actually do before it broke" has an answer you can grep.

Evidence, not assurances

An agent saying "fixed!" is weather forecasting; an agent showing the test going green is meteorology with instruments. Willison's bar for agentic work is that the agent must exercise what it builds — boot the server, curl the API, capture the output — and show that evidence rather than assert success; his Showboat workflow turns that requirement into an artifact the agent assembles as it works. Adopt the same standard for your own sessions: no acceptance without output pasted. And you do not have to improvise this discipline each time — Jesse Vincent's superpowers library ships debugging as a packaged skill whose root-cause-tracing procedure walks the agent backward through the call stack before any fix is proposed. Loading a written procedure beats hoping the model invents one under pressure.

Which brings the lesson home. Watch a session refuse to reproduce anything and just… try things. Your job is to spot the moment and choose the hatch.

warning

Three speculative fixes stacked on top of each other is not debugging — it is archaeology. Each unverified fix adds a layer between you and the original failure, multiplies the diff nobody can review, and can introduce its own bugs (see pass 4 above). The stack never gets smaller by adding to it. Count the corrections: two misses is the documented signal to restart, not a reason for a third attempt in the same direction.

Where this lands in your build

This is not hypothetical for the threaded builds: when the compass calculator printed $0.26/M blended while the hand-math disagreed, the reproduce-first move already existed — npm run verify replays three pinned math cases and names the failing one, turning "the numbers look off" into a specific red assertion before anyone theorized. Keep that pattern in every build: a pinned-case verifier committed alongside the feature means breakage gets replayed, not remembered.

§8

Try it yourself

  1. Exact-click checkpoint. Run the bisect race above to completion with BOTH strategies, noting your move counts. Then open git-scm.com/docs/git-bisect, find the git bisect run section, and write down what exit code 0 means, what 125 means, and what any other non-zero code means. You have just read the automation contract for the game you played.
  2. Break it on purpose. Make a throwaway folder, init git, and commit a tiny script 16 times, changing one number in commit #7 so a one-line check (node check.js exiting 1 on failure) catches it. Run git bisect start, mark HEAD bad and the first commit good, then git bisect run node check.js. Watch git name commit #7 in about four automated steps.
  3. Ship-sized task. Next time your real build breaks in an agent session, impose the law: no fix proposals until a written repro recipe exists, and a failing test before any edit. Count the agent's correction attempts aloud — when you hit two misses, run the hatch: restart the session with the exact error text as your opening line.
§9

Self-check

Why is a suppressed error usually worse than a crashing one?

A crash announces itself at the scene — stack trace, line number, reproducible state. A suppression (silent catch, default-value fallback) lets execution continue in a state the programmer never reasoned about, so the real failure surfaces somewhere else, later, with no breadcrumb pointing home. Fix root causes; treat suppression as moving the bomb.

Two corrections have failed and the diff is growing. What now, and in what order?

Official rule: two failed corrections means stop correcting. Order: revert the speculative commits to last-known-good (they are unreviewable stacking), then start a fresh session — /clear — pasting the exact error text first, and demand a repro recipe plus failing test before any new edit. Rewind/checkpoints get you back even cheaper if the harness offers them.

When is bisection the wrong tool?

When you have no automatic oracle — bisection needs a scriptable good/bad answer, so a bug that only reproduces through manual clicking must first be pinned by a test (or you burn hours hand-testing midpoints). Also wrong for unordered or nonexistent history, and for nondeterministic failures whose good/bad verdicts lie. Repro-first is not optional even here; it is what makes the verdicts truthful.

§10

Beyond this build

Production incidents. The same skeleton scales up: practitioners running fleets of production agents describe normalizing trajectories (each run becomes a comparable record), isolating the earliest failing step, and replaying failures as test artifacts so one incident becomes a permanent regression case. Flagged honestly: that write-up is a solo engineer's synthesis, not peer-reviewed research — borrow the shape, verify on your own systems.

Reading stack traces backward transfers everywhere — agent sessions, CI logs, a stranger's bug report. The throw site tells you what broke; the deepest frames tell you why. Start at the bottom of the trace and climb toward the noise.

Delete and rewrite. Sometimes the cheapest hatch is the scorched one: when the accumulated diff costs more to understand than the component costs to rebuild, deleting and regenerating from a clean spec — with the failing test kept safe — beats forensic repair. The discipline stays identical: reproduce, pin with a test, then decide whether the fix is a scalpel or a bulldozer. Bisection, hatches, evidence — all of it works the day after the framework you learned it on is obsolete. That is the point.
