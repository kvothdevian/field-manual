Six shapes, one baseline

Before the five named patterns, the zeroth option: do nothing clever. One direct prompt, one session, a clear stopping condition. If that works — and it works far more often than beginners expect — you are done. Every pattern below is a purchase: more tokens, more latency, more parts that can disagree. Buy only with a reason.

The five names come from Anthropic's building effective agents essay — the pattern-namers' own engineering blog, cited here as vendor material:

  • Prompt chaining — decompose into fixed substeps, each feeding the next: gather → draft → check. Predictable and inspectable; worth it when the steps are genuinely distinct.
  • Routing — classify the input first, send each class to a specialized handler. Buys focus; costs you a classifier to maintain.
  • Parallelization — split one job into independent pieces (sectioning) or run candidates side by side and vote. Latency drops; disagreement becomes signal.
  • Orchestrator-workers — a planner delegates to workers who cannot see each other. Strong on genuinely separable work; brittle when subtasks share hidden state.
  • Evaluator-optimizer — one model generates, another judges against criteria, loop until it passes. The only pattern that manufactures judgment where no test exists.

tip

Premature orchestration kills more sessions than weak models do. Before adding any stage to a workflow, name the specific failure it catches. If you can't name it, you're buying vocabulary, not reliability — ship the boring version.

warning

Verification debt compounds. Every unverified hand-off between stages multiplies into the next stage's inputs; by the time symptoms surface you can no longer attribute the failure. Verify at every seam — especially the seams you paid extra to create.

§3

Spec-driven development: rules before code

When a task outgrows one sitting, the patterns need raw material: a spec. GitHub's Spec Kit turns that into a typed pipeline — /speckit.constitution records the project's non-negotiable principles, specify captures what and why while explicitly excluding technology choices, plan owns those technical decisions grounded in the constitution, and tasks breaks the work into ordered, checkable chunks. The launch essay's slogan is the right mental model: intent is the source of truth. The contributor deep-dive adds two corrections worth keeping: the constitution is what grounds the plan, and this is not waterfall — you re-enter any command when reality argues back.

Right-size it. A constitution for a weekend script is ceremony; the simplest-sufficient rule applies to process shapes too. Scale the spec's weight to the blast radius of getting it wrong.

§4

Tests as the steering wheel

The cheapest control surface for any pattern is a test the agent must satisfy. Willison's red-green guide reduces it to a one-line prompt: write a failing test first, confirm it fails, then make it pass. The confirmed failure is the point — it proves the test can fail, which is what separates a steering wheel from a participation trophy, and it prevents both broken code and dead code nothing ever exercised.

Flip the order and meet the tautology trap: tests written after the code tend to encode the model's own misreadings, producing green lights that prove the code agrees with itself. Practitioner defenses: treat contract-style tests as reviewable specification, and audit suites for hermeticity — tests that fake their inputs verify nothing about the world.

§5

Evals before iteration

When no unit test can express "good enough," you need an eval, and Hamel Husain's field guide is the on-ramp: climb the ladder from unit assertions to human or LLM judging to A/B comparison — and know that missing evals are the single most common stall point in AI projects. One discipline matters above all: if a model acts as judge, align it against human labels on 25–50 examples first. An unaligned judge doesn't optimize quality; it optimizes noise, loudly.

§6

Reflexion, with an expiry date

One peer-reviewed cousin belongs in your toolkit: Reflexion showed agents that verbally reflect on a failure — a short written post-mortem held in an episodic buffer — improve on later trials, lifting HumanEval pass@1 from 80% to 91% at publication. Treat those digits as historical: they predate modern harnesses by years. The durable export is cheaper than the benchmark — between attempts, write down what failed and why instead of blindly retrying.

§7

The gauntlet: the book's own engine

Honest labeling first: the gauntlet is this book's house pattern, and it has no quantitative validation — no study benchmarks it. Its nearest studied anchors are the evaluator-optimizer pattern above, Reflexion's reflection loop, and Hamel's judge-alignment discipline. We present it as practitioner craft, with the book itself as the running evidence.

Mechanics, exactly as this project runs them:

  • Builder and critic are separate agents with fresh contexts. The critic never inherits the builder's rationalizations — empty transcript, clean eyes.
  • The critic fetches real bars. Named, fetchable artifacts — for this book, Bartosz Ciechanowski's essays for visual craft and Anthropic's Claude Code best-practices page for content authority.
  • The comparison is blind. Labels stripped; the critic sees two anonymous candidates and picks a winner.
  • Verdicts are binary — which one wins, plus the single biggest gap. No scores; numbers invite negotiation.
  • Exit = the critic picks ours blind, or the human stops the run. Never exit on a round count — "three strikes" exits are how losing entries ship.

§8

Plan-first mechanics

Under every pattern sits one harness habit: think before edits. Official workflow docs prescribe the shape — a read-only plan mode where the agent explores and proposes, you approve before any file changes, and research is delegated to subagents so your main context stays clean for decisions. Planning is the cheapest pattern you own: it spends tokens to save rewrites.

§9

Where this lands in your build

quiz-forge, the two-week build, gates AI-generated quiz questions through human-review batch gates: the agent produces a batch, you judge the batch against the spec's bar, and each batch lives or dies whole. That is the evaluator-optimizer pattern with a human judge — and per the evals discipline, you will calibrate your own judging on a small aligned sample before trusting your gut at volume.

§11

Try it yourself

  1. Exact-click checkpoint. Open anthropic.com/research/building-effective-agents, scroll to "Building effective systems," and copy the five workflow-pattern names into your notes with one line each. Then play the picker above until the counter reads 4/4 — including finding the deliberately wrong assignment and reading its trace twice.
  2. Break it on purpose. Assign orchestrator-workers to the failing-test chore, then write down every point in the trace where a decision dispersed. Next, take one real failing test in your own project and fix it with a single direct prompt. Compare wall-clock times and diffs.
  3. Ship-sized task. Take one real step toward quiz-forge. Write its stopping condition, choose the simplest sufficient pattern, run it, and log three lines: which pattern, why, and whether a simpler one could have done the job. Keep the log — it becomes your pattern intuition.
§12

Self-check

Name the baseline plus the five workflow patterns.

Baseline: one direct prompt, no structure. Then chaining (fixed substeps in sequence), routing (classify, dispatch), parallelization (split or vote), orchestrator-workers (planner + insulated workers), evaluator-optimizer (generate, judge against criteria, loop).

Why can't you write the tests after the code and call it verified?

Because tests written against finished code tend to encode the model's own misreadings — a tautology. Green then proves the code agrees with itself, not that it's correct. Write the test first and watch it fail; the confirmed failure is the proof the test can bite.

A teammate proposes a three-agent pipeline to fix a typo. What do you ask?

What specific failure does each extra stage catch? If there's no answer, it's premature orchestration — plus compounding fragility from unshared context. The burden of proof sits on complexity: measure the simpler version failing before buying more machine.

§13

Beyond this build

Scaling to teams. Personal patterns harden into team conventions: a private constitution becomes a team charter, batch gates become review queues, and the gauntlet's named bars become the org's published standards. The mechanics survive the scaling; only the judge changes — from you, to whoever holds the bar.

Agentic CI. The same loops, unattended, on every push: evaluators gating merges, critics filing review comments, gauntlets running overnight. That is Chapter 12's territory — pipelines that prevent bloat — and everything there assumes the pattern-selection discipline you built here.

When patterns become ceremony. The tell is a stage nobody can justify: ask "what does this catch?" and listen for silence. Delete stages that exist for vocabulary's sake. And keep Anthropic's boundary in view: these five are workflow shapes — predictable, human-directed. A genuinely autonomous agent is a different, more dangerous beast, and it owes you the same answer to the only question that matters: what measurable failure justifies it?
