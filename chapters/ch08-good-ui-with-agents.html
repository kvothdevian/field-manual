Promise: after this chapter you can get non-generic, accessible UI out of an agent — by feeding it constraints (tokens, component contracts, a screenshot loop) instead of vibes.

Ask three agents, on three days, for "a clean modern landing page," and watch them converge: white canvas, placeholder-grey captions you can barely read, one deeply familiar shade of blue, soft blur shadows, generously rounded everything. The models aren't coordinating. With no local constraints, a language model regresses to the median of everything it has ever seen — and the median of the training data is precisely the generic interface you didn't want.

The inverse observation is the good news. Simon Willison's first-person account from the March 2026 Pragmatic Summit records that inside a codebase with established conventions, agents follow the existing patterns "almost to a tee." Hold the two facts together and the whole chapter falls out: the pattern-following machinery is the product. Give it patterns and imitation becomes leverage. Give it nothing and the median ships. So we supply patterns — three constraint layers any agent can consume, plus the accessibility floor that converts "looks fine" into a measurement.

Constraint layer one: design tokens

A design token is a named value — a color, a radius, a spacing step — stored as data, separate from any stylesheet. For an agent it works as a machine-readable guardrail: the model doesn't have to interpret adjectives like "warm," it resolves --paper to #F6F1E7 and stops improvising. Off-palette choices don't get argued against; they become unwritable, because every rule references a token instead of a literal.

Honesty about maturity, per this book's protocol: the Design Tokens Community Group's format is published as a Community Group Draft Report — the de facto interchange standard for tokens, and explicitly, deliberately not a W3C Standard. Adopt it as the lingua franca between humans, agents and build tools, but verify your pipeline's importer before betting a release on it:

{
  "color": {
    "ink":   { "$type": "color", "$value": "#201B14" },
    "paper": { "$type": "color", "$value": "#F6F1E7" }
  },
  "radius": {
    "card":  { "$type": "dimension", "$value": "12px" }
  }
}

Hand a file shaped like that to an agent before line one and "make it fit the brand" stops being a mood board and becomes a lookup.

Constraint layer two: component contracts

Tokens pin the raw materials; component contracts pin the assembled parts. The shadcn/ui docs state the quiet part out loud: open code you copy into your own repo, written to be predictable "for your team and LLMs" — an explicit AI-readiness claim, not a retroactive one. When a button, a dialog, a card already exist as readable source, the instruction "use the existing dialog, don't invent one" is enforceable: the agent can read the contract and compose instead of reinvent.

Utility-CSS frameworks play the same game at a finer grain. Tailwind's utility classes plus theme variables act as a constraint lattice for generated CSS: every color the agent writes routes through something like bg-primary, resolved by the theme, so an off-palette hex has nowhere to land. None of this requires Tailwind specifically — the generalizable move is make the compliant path the path of least resistance. An agent greedy for the shortest output will take the lattice you built if inventing freehand costs more tokens than obeying.

Constraint layer three: the accessibility floor

WCAG 2.2's quick reference is the floor, not the ceiling. Two rows matter most day to day, both from Success Criterion 1.4.3 (Contrast, Minimum): text needs 4.5:1, large text — at least 24px regular or roughly 18.66px bold — needs 3:1; the enhanced criterion 1.4.6 raises normal text to 7:1. Contrast is arithmetic, which makes it the perfect acceptance test for agentic UI: no taste required, only math. The ratio comes from relative luminance:

linearise each channel c ∈ [0,1]:
    c ≤ 0.03928 ? c / 12.92 : ((c + 0.055) / 1.055) ^ 2.4
L  = 0.2126·R + 0.7152·G + 0.0722·B
ratio = (L_lighter + 0.05) / (L_darker + 0.05)

warning

Screenshot loops without acceptance criteria are infinite polish. "Make it closer to the mock" has no finish line, so the loop eats your token budget redesigning the same card forever. Name the done: these five pairs must clear 4.5:1, these elements must use these tokens, the flow must survive 360px. Then the loop converges — or you stop it.

The screenshot loop, prescribed

Constraints tell the agent what good means; the loop lets it check. Anthropic's Claude Code best practices prescribe this formally: hand the agent a design mock or screenshot, let it take screenshots of its own result, compare against the target, fix, iterate — and verify UI changes visually instead of trusting that a diff "should" render right. This is the same bounded loop Chapter 01 taught with goals and stopping conditions, pointed at pixels.

Two maintained bridges give the model eyes. ChromeDevTools' chrome-devtools-mcp drives a live app: screenshots, console messages, DOM snapshots, performance checks — roughly 50k stars at checking time. Microsoft's playwright-mcp is the accessibility-tree alternative: instead of pixels, the model reads a structured snapshot of the page, and the project's own README weighs the MCP-versus-CLI tradeoff rather than hiding it. Screenshots judge aesthetics; accessibility trees judge structure — serious UI loops use both.

you   → build the quiz card from journey/design.md · done = every
        token rule passes at a 360px viewport
agent → screenshot taken · three diffs vs the token sheet:
        1. card radius is 18px vs tokens say 12px
        2. focus ring invisible on ink buttons — ink outline, ink fill
        3. answer tap target 32px < 38px floor
you   → fix all three against the sheet · change nothing else
agent → second screenshot taken · radius snapped to 12px, focus ring
        re-cut in paper with offset, targets at 44px · diffs clear
one cycle of the screenshot-compare loop · an authored example shaped from real sessions — your transcripts will differ
tip

Give the agent YOUR tokens before line one. Sixteen lines of token JSON pasted into the first message (or better, an AGENTS.md) costs less than one round of "no, not that blue," and every later session inherits it for free. Constraints compound; corrections churn.

Where this lands in your build

Your current threaded build — ncert-quiz-forge, Build 2 in the companion specs — never asks its agents what the brand looks like, because the answer is already machine-readable. Its BUILD.md binds the UI to the journey site's design.md, and this is the actual block it inherits, verbatim:

:root {
  --paper:        #F6F1E7;   /* page background */
  --paper-raised: #FFFDF7;   /* cards, tickets, station nodes */
  --ink:          #201B14;   /* text, borders, primary buttons */
  --muted:        #6F6455;   /* secondary text (≥4.5:1 on paper) */
  --line-strong:  #CBBFA9;   /* dashed rules, ghost borders */
}

Two details worth savoring. First, the spec's frontend section already encodes this chapter's floor: correct/incorrect feedback uses jade and coral with ✓/✕ glyphs — shape plus label, never color alone — and demands large touch targets for students on phones. The agent didn't decide that; the contract did. Second, a drift confession: the journey's --muted is #6F6455; this book's vendored copy quietly darkened it to #5F5648 for extra AA headroom — run both through the lab above and you'll see why. DESIGN.md's own preamble orders deliberate reconciliation whenever the upstream file changes. Tokens drift; the discipline is noticing.

Status honesty: the forge's M1a scaffold landed 2026-08-25; the quiz UI this block governs is milestone M4, gated behind human-reviewed content batches. The tokens ship before the screens they style — that ordering is the whole technique.

Try it yourself

  1. Exact-click checkpoint. In the lab above, pick plum (#8E5BA6) on paper and read the number before the verdict — predict pass/fail, then check. Repeat with the banned blue on white. Write both ratios down: one misses AA by 0.06, and watching a threshold beat you by a hair teaches more than any lecture on "close enough."
  2. Break it on purpose. Paste the six-token block from the build section into your agent with "restyle this button using ONLY these tokens," then ask again with no tokens at all. Diff the two outputs — count how many decisions you had to make by hand in round two.
  3. Ship-sized task. Create tokens.css in your own project with at least four named values, reference it from AGENTS.md, and require every color in new CSS to arrive as a var(). Then run the lab's math on every text/background pair the agent produced. Fix the failures by changing tokens, not components.

Self-check

Why does an unconstrained agent produce generic UI — is the model bad at design?

The opposite: it's good at patterns. With no local conventions, generation regresses to the statistical median of its training data, and the median web page is beige sameness. Willison's observation cuts both ways — agents follow existing patterns "almost to a tee," so the fix is supplying patterns, not wishing for taste.

Plum on paper measures 4.44:1. Why is "visually identical to passing" not good enough?

WCAG thresholds are hard floors, not suggestions: 4.44 fails SC 1.4.3 for normal text, full stop. Binary cutoffs are a feature for agentic work — they turn taste into an acceptance test an agent can evaluate mechanically, and the large-text carve-out (3:1) gives you a legitimate second lane instead of a rationalization.

When is a screenshot loop actively harmful?

When it runs without acceptance criteria. "Get closer to the mock" never terminates, so polish cycles burn budget without a done state. Bound every loop with measurable exits — named contrast pairs, token conformance, a minimum viewport — and stop when they pass or the budget dies.

Beyond this build

Mobile-first checks. The screenshot loop earns its keep twice on phones: drive the viewport down before judging anything, because layouts that survive 360px force hierarchy decisions that desktop hides. Both browser tools above can resize and re-capture; make the narrow pass a named acceptance criterion, not an afterthought you'll "get to before ship."

When to hire a designer. Constraint layers systematize execution; they don't originate identity. If your product needs a distinctive brand, a novel interaction paradigm, or judgment about what a feature should be, that's designer territory — bring one in to author the tokens and contracts, then let agents scale them. Hiring execution pixel-pushers after the system exists is the spend most solo builders can skip.

Design systems at team scale. Everything here compounds: tokens become the organization's API for look-and-feel, the CG Draft format becomes the interchange between design tools and code, and CI gates — contrast checks, token lint rules — enforce what documentation alone never did. Where it breaks down: systems ossify. Schedule token reviews like dependency updates, or your guardrail becomes the new generic.
