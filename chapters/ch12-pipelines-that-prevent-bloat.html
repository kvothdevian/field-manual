Chapter 12 · Pipelines that prevent bloat

facts checked as of 2026-08-26

gates reviewers bots calendar in your builds exercises

Promise: after this chapter you can wrap your agent workflow in gates that keep a project healthy for months — bloat becomes something the pipeline catches, not something you notice too late.

Every project rots by default, and "bloat" is bigger than file size. Builds break. Dependencies fall behind and collect vulnerabilities. Links die. The README describes a program that no longer exists. The spec promises a page the code never shipped. None of this arrives as an alarm; it arrives as a slow tax on every future session — and coding agents quietly raise the rate. An agent never feels embarrassed by the stale README, so it trusts it; the next session inherits yesterday's drift as today's facts. You met this in Chapter 01 as stale breadcrumbs and bloated memory files. Willpower will not fix it — vigilance fails by week three. Plumbing will.

§1

A gate is a check that runs so you don't have to remember

Tool-agnostically, a delivery pipeline is one idea: every change enters the project through the same doorway — a branch turned into a pull request — and the doorway is rigged with gates: automated checks that run on arrival. A good gate has three properties. It is automatic (no willpower involved), binary (exit code, not vibes — the verify ritual from Chapter 01, industrialized), and fast (feedback while the change is still fresh in anyone's head). Five families of gate cover nearly everything that rots, staged by rising cost of adoption:

  • Correctness — does it build, do tests pass. Catches the most common agent failure: plausible code nobody ever ran.
  • Hygiene — link checkers, formatters. Catches decay nobody commits but everybody creates.
  • Currency — dependency bots filing upgrade chores as tickets-with-diffs attached.
  • Drift — scheduled jobs that compare documentation and specs against reality, on a calendar instead of at merge time.
  • Review — a human, or a bounded agent, reading the diff before it merges. Last: the expensive, nuanced gate.

tip

Add the cheapest gate first: the build must pass. It is a few lines of CI config, costs almost nothing to maintain, and intercepts the single most frequent way agents ship damage — code that looks done and was never executed. Stage the rest by rising cost: link check, dependency bot, scheduled sync, and agent review last, because it is the expensive, nuanced one.

A pipeline you grow one cheap gate at a time survives; one you try to install wholesale usually doesn't.

The thesis gate is paste-sized too. Save this generic template as .github/workflows/build.yml and every pull request runs the build — swap the two run: steps for whatever "it builds" means in your stack:

# .github/workflows/build.yml · generic-template · cheapest gate first
name: build
on: pull_request
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: npm ci
      - run: npm run build
§2

Reviewers that never tire — but must be bounded

The review gate no longer has to be you-alone. Anthropic ships an official Claude Code GitHub Action: mention @claude in a pull request and a bounded agent investigates the diff, asks questions, and can push fixes; an automation mode lets it act on triggers such as new issues, and a --max-turns setting caps how many agentic turns each invocation gets — which is exactly what it sounds like, a spending limit on autonomy. Authentication rides in GitHub secrets; the action is MIT-licensed, works with Bedrock/Vertex/Foundry backends, and its repo carries a security guide whose three headings are worth memorizing: access control (who can summon the agent), least-privilege permissions (what it may touch), and verified commits (signed, so its output is attributable). OpenAI's answer lives in the cloud: Codex cloud tasks — delegable with @codex, runnable in parallel, with first-class PR-review flows — driven by the same agent as the Apache-2.0 Codex CLI, signed in with a ChatGPT plan or an API key.

The honest caveat comes from Chapter 01 and never expires: accountability stays human. An agent reviewer is a tireless first pass that catches the mechanical sins — scope creep, missed call sites, untested paths — while you keep the judgment calls. Bound its turns, restrict its permissions, read its findings, and it compounds your attention instead of replacing it.

§3

Bots that file the chores

Currency gates are solved problems; adopt them rather than hand-roll them. GitHub's Dependabot reads a dependabot.yml and files upgrade PRs on a schedule — and it covers more than libraries: the github-actions ecosystem updates the pinned workflows themselves, closing the loop where your pipeline's own skeleton ages:

# .github/dependabot.yml — two ecosystems, one chore queue
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"

Renovate is the multi-platform alternative — GitHub, GitLab and others — with fine-grained scheduling and shareable config presets; it is AGPL-3.0 and maintained with public docs. Pick one bot per ecosystem and stick with it; Chapter 12's Beyond section names the fight you start if you run two.

§4

The pipeline on a calendar

Merge-time gates cannot catch what time breaks. Drift needs a clock: a scheduled job (a cron trigger in Actions, or any scheduler) that wakes up weekly and hands an agent a comparison task — docs against routes, README setup steps against scripts, spec against shipped behavior — and opens a small PR with the deltas. Anthropic's official solutions guide publishes exactly these recipes: recurring docs-sync, issue triage, and scheduled maintenance jobs run by the same action that reviews your PRs. This is the gate aimed at the bloat that hurts agents most: a stale README doesn't just embarrass humans, it actively programs the next session wrong.

Six-week verdict

Three things to notice before you go. First, the asymmetry: catches are tiny and boring — one green tick per week — while lands are invisible until they compound into a debt board. Second, the runs are identical, only the safety net differs; that is precisely how you should evaluate gates on real work, same project, with and without. Third, overhead is real even when it pays: automation spends minutes every single week whether or not anything breaks, which is why the cheapest-first ordering in the tip above exists.

warning

A gate nobody reads trains bypass habits. A red build that stays red gets click-past, a reviewer who nitpicks formatting gets muted, a bot that files ten noisy PRs a week teaches the team to close without reading — and then the one PR that mattered sails through on trained reflexes. Keep the gate list short, every signal loud and actionable, and delete gates that cry wolf. A pipeline's authority is spent exactly like yours: one ignored warning at a time.

Try it yourself

  1. Exact-click checkpoint. In any GitHub repo you own, click Add file → Create new file, name it .github/dependabot.yml, paste the eleven-line config above, and commit to main. Return the following Monday: Dependabot will have filed its first chore PRs — your first currency gate, installed in one paste.
  2. Break it on purpose. Run the incubator twice on scenario A: once bare, once with only the CI build check on. Before the second run, write down which week you expect the gate to pay for its own overhead. Check the prediction against the verdict — then explain to yourself why the other weeks' overhead wasn't wasted.
  3. Ship-sized task. Give one real project its first gate this week: a build check. Branch, commit a ci:-prefixed workflow file in the smallest PR the platform allows, and watch it run. Then deliberately push a commit that breaks the build and confirm the door actually slams — an untested gate is a rumor, not a gate.

Self-check

Why is "build must pass" always the first gate?

Highest ratio of caught-to-cost. It is nearly free to install and maintain, and it catches the most frequent agent failure — plausible code that was never executed. Every other gate costs more per week and catches rarer rot, so the ordering is strict: earn trust with the cheap binary gate before paying for nuanced ones.

What distinguishes PR-time gates from calendar gates?

PR-time gates (build, links, agent review, dependency bumps) judge a change at the only moment reverting it is cheap. Calendar gates (docs-sync, scheduled maintenance) judge time's effect — hosts dying, specs drifting, READMEs aging — which no merge can trigger because no single change caused it. Healthy pipelines run both.

Name two ways a pipeline itself becomes the bloat it fights.

Unread signals: a chronically-red gate or noisy bot trains the team to bypass checks, so real failures sail through. And runaway autonomy: an agent reviewer or recurring job without a turn/spend cap (the --max-turns problem) burns budget every run regardless of whether anything needed doing. Few gates, loud signals, hard bounds.

Beyond this build

Monorepo scale. One giant gate-suite per PR stops scaling fast: every typo would rebuild everything. The standard move is path-scoped pipelines — checks fire only for packages the diff touches. Same principle as repo maps (Chapter 11): spend verification budget where the change landed.

When bots fight each other. Run Dependabot and Renovate on the same manifest and they will race: dueling bump PRs, lockfile conflicts, rebases eating an afternoon. Assign exactly one bot per ecosystem and mute or evict the other; duplication is not redundancy, it is two machines generating review debt for each other.

From solo ritual to team contract. Everything here scales upward unchanged: required status checks turn your personal verify ritual into policy, CODEOWNERS route specific paths to specific humans, and agent reviewers become the tireless first pass ahead of human review. What does not scale down again is the culture — a team that treats green checks as bureaucracy will get the bureaucracy it deserves.

Where it breaks down. Flaky gates train bypasses faster than no gates at all. No gate can judge taste — a pipeline proves the build passes, not that the product is good. And an agent reviewer, however bounded, inherits blind spots from its context: it verifies what it can see. The Chapter 01 rule survives automation intact — accountability stays human; the pipeline just makes the evidence arrive on time.
