Chapter 05 · Context engineering

Promise: after this chapter you can keep an agent session sharp for hours — by managing what enters context, what gets compacted, and what carries across sessions.

facts checked as of 2026-08-25 · all token figures here are teaching approximations, proportionate to published measurements — your harness's real counts differ

Context is a budget, not a bucket

Chapter 01 established that the agent re-reads its entire transcript on every pass of the loop. That transcript — the context window — is not a warehouse where stuff accumulates harmlessly. Treat it as a finite attention budget. Anthropic's engineering essay on context engineering puts it plainly: the goal is finding the smallest set of high-signal tokens that keeps the task solvable, because attention shows diminishing returns as volume grows. The craft is not "fit more in." It is keeping signal density high enough that the right facts win the model's attention on pass forty, not just pass four.

The same essay names three levers for long-horizon work: compaction (collapse history, keep conclusions), structured note-taking (persist facts outside the window), and sub-agent architectures (do heavy reading in a separate window, bring back a summary). This chapter is those three levers, plus the discipline that comes before all of them: deciding what you let in at all.

The evidence that length costs accuracy

Why budget at all? Because measured performance degrades with input length — even on trivial tasks. A 2025 study from Chroma Research tested eighteen state-of-the-art LLMs and found accuracy falls non-uniformly as context grows, with distracting material compounding the damage. Read the sourcing honestly: this is vendor research, marketing-adjacent by nature — but it was controlled, published with public replication code, and nobody has produced a credible reversal. The practical takeaway stands: a bigger window is storage, not immunity. A million-token context (remember Gemini's free tier from Chapter 03?) will hold everything and still attend to it worse. Degradation starts long before the wall.

What actually enters your context

Before you typed a single word today, your agent's window already held: a system prompt the harness authors wrote, your memory and instruction files, one-line descriptions of every installed skill, and — the sleeper — the API schemas of every connected MCP server, because the model needs to know which tools exist and how to call them. Official Claude Code documentation itemizes exactly this loading order. Then comes what the loop itself writes: your prompts, the agent's reasoning, every tool call, every file read, every command's full output. Two kinds of load result:

  • Standing rent — charged every session, whether or not you use it: system prompt, memory, skill descriptions, MCP schemas.
  • Working history — everything accumulated this session: pasted files, tool output, back-and-forth turns.

Compaction: what /compact actually does

When history crowds the window, harnesses offer compaction. The documented semantics: /compact replaces the whole conversation with a structured summary, then rebuilds a fresh context around it — your instruction files re-read from disk, so your rules survive even though your chat log did not. Any skill bodies you had invoked come back too, capped at roughly five thousand tokens. Hooks exist around the moment (Claude Code ships a PreCompact hook; opencode exposes an experimental session.compacting plugin event) so teams can inject continuation notes before the squeeze. Numbers vary by harness; the mechanism does not.

Now the trap the sandbox staged: compaction collapses history only. Standing rent — system prompt, schemas, skill descriptions — re-presents in the rebuilt context, every single time. You cannot compact your way out of a fat MCP server. Harness documentation says this out loud: opencode's own MCP docs warn that a GitHub MCP server can easily exceed the context limit by itself, and prescribe disabling or globbing-off servers you are not using. The cure for bloated rent is eviction at the config layer (Chapter 04's tools), not compression at the session layer.

Memory that crosses sessions

Compaction saves a session; memory saves you. Documented behavior in Claude Code: an index file (MEMORY.md) loads into context every session, and richer auto-memory directories persist per repository — shared across git worktrees, scoped to your machine, never synced anywhere. Chapter 04 taught you to write such files; here is the economic frame that makes them matter: memory is standing rent, so it competes for attention with everything else — which means you write conclusions, not transcripts. "Tests: npm test, never tsc alone" earns its ninety tokens every day. Yesterday's error dump does not.

Subagents: the pressure valve, honestly sold

The third lever attacks the deepest problem: research-heavy steps that flood history with material you need once. The documented mechanics quantify the win precisely — in Claude Code's example, a subagent reads 6,100 tokens of files inside its own window and returns a 420-token summary. The parent pays 420, not 6,100; the subagent doesn't even inherit the parent's memory directory. Multiply that across a dozen exploratory reads and the difference between a sharp session and a rotten one is arithmetic.

But hold the counterargument before adopting the hammer. Cognition — the Devin team — published the canonical dissent: naive multi-agent splitting produces fragile systems, because an agent's actions carry implicit decisions, subagents on conflicting context make contradictory choices, and nobody holds the full trace. Both essays are vendor opinion pieces, and they genuinely disagree. The synthesis this book teaches: delegate breadth (search, enumerate, summarize — mechanical lookup where the subagent's decisions get reviewed anyway), keep judgment (architecture, tradeoffs, anything irreversible) in one thread where one trace carries every implicit decision. Isolation is a pressure valve, not a philosophy.

tip

Start every session by stating the finish line — the same falsifiable stopping condition from Chapter 01. It costs twenty tokens up front and pays for the whole session: a stated goal keeps every subsequent pass pointed at something, which is the cheapest attention-sharpening move that exists.

warning

Kitchen-sink sessions rot fastest: five features, one endless thread, quality sagging until the agent contradicts decisions it made an hour ago. The sandbox just showed you the mechanism. The fix is procedural, not clever: one goal per session, compact or restart at natural milestones, and treat a fresh start as cheap maintenance — usually it beats rescuing a bloated thread.

The agent-cost-compass repo stays deliberately tiny — a handful of files — so its sessions stay cheap: little standing rent, short histories, rare compaction.

Try it yourself

  1. Exact-click checkpoint. In the sandbox above: tick every box including the github server, press work a few turns eight times, and read the sharpness chip aloud. Press run /compact and find the three lists — collapsed, survived, returned. Then uncheck github and read the floor line again.
  2. Break it on purpose. Before touching anything, predict: with the github server on versus off, which setup does /compact help more? Write the prediction, then run both. Compaction recovers history either way — the floor difference proves the rent was never the history's fault.
  3. Ship-sized task. Open your real project folder. List what loads unasked: MCP servers configured, skills installed, your instruction file's length. Disable one server you have not invoked in a week. Next live session, run /compact mid-task and read what it kept — compare against the sandbox's survived/returned lists.

Self-check

Your session feels dull and you ran /compact twice. Why might it still be dull?

Because compaction only collapses history. If most of your load is standing rent — a heavyweight MCP schema, a bloated instruction file — the rebuilt context re-inherits all of it. Evict rent in configuration; compact only fixes accumulation.

A subagent reads 6,100 tokens of code. What does the main session pay?

About 420 tokens — the summary. The reading happened in the subagent's own window, which doesn't even inherit your memory directory. That ratio is why research breadth belongs behind subagents while decisions stay in the main trace.

When is fanning out subagents the wrong call?

When the steps carry implicit decisions that need one shared trace — architecture choices, sequencing, taste. Cognition's critique: split contexts make contradictory choices nobody can reconcile afterward. Fan out lookup, never judgment.

Beyond this build

Long-horizon projects. Multi-day epics — migrations, spec-driven builds (Chapter 06) — outlast any window. The pattern: keep a running notes file on disk (findings, decisions, open questions), let compaction eat the transcript, and re-anchor each morning's session with one pointer to that file. The notes are the session's successor; the transcript was scaffolding.

Note-taking patterns. Structured task lists the agent checks off, decision logs appended rather than rewritten, and summaries written by the agent, to disk before a planned compaction — all formalize the same instinct: move conclusions out of volatile memory into durable, re-loadable form. Memory files are the permanent tier; session notes are the project tier.

When to just restart fresh. Signals: the agent re-reads files it read an hour ago, contradicts earlier decisions, or edits sprawl beyond the stated goal. A fresh session with a good memory file and a one-paragraph handoff note routinely outperforms nursing a rotten thread — the window resets, the knowledge stays. Restarting is not failure; it is the cheapest compaction there is.
