Session 09 · testing agent builds · opencode default

Testing what agents build

Refuse every agent-written green suite until you have watched it fail, and name the change that would turn each test red.

60 min · scratch repo · needs ch06 · verified 2026-09-04

Briefing · 5 min · proof before belief

i.Ship the function with its proof

A green test suite is not proof that code works. It is proof that code satisfies the assertions somebody wrote — and when the same agent wrote both, that somebody agreed with itself. The proof this session demands is narrower and stronger: a failure you watched fail, then pass. Run the tests before the implementation exists, capture the red, then implement until green. The red is the receipt that the test can detect anything at all.

Order is the instrument. A test written first, from the specification alone, is a specification in executable form: it pins behavior the code must grow into. A test written after, from the code, is a biography: it describes whatever the code already does, defects included. Tests learned from code agree with code — that is not verification, it is transcription. The largest study of agent-generated tests to date found the failure is subtler than shallow coverage: agent suites check more edge cases than human ones yet go flaky more often, because they touch clocks, filesystems, and randomness instead of isolating them. Broad coverage you cannot trust, plus a suite that trains the team to ignore red.

"It passed" is a claim; command plus output is a fact. From here on, no task is done without both: the exact command typed and the output observed, pasted where another person can replay it. Agents narrate success fluently; only command output keeps them honest.

The same habit travels to two harder venues. In the browser, per-action traces record what the agent actually did — screenshot, DOM, network, console for every step — reviewable without reading a line of code. Where behavior is fuzzy and no boolean fits, evals-lite applies: a task, a grader, and an outcome, a handful of graded examples beating vibes every time, reading transcripts instead of aggregates. And the conformance trick compresses all of it into one line: build the passing suite against several independent implementations first, then implement yours against the suite.

Where it breaks down: suites rot as code drifts and nobody re-reads assertions; specifications have blind spots that tests inherit silently; fuzzy behavior resists booleans, which is exactly what graders are for. None of this removes the mandate. It explains why the mandate needs maintenance.

ii.Order is the instrument · specification vs biography

The defect below is identical on both tracks: division by zero returns 0 instead of throwing. On the left track the test was written from the held specification, so the defect dies at birth — the suite was already red on that behavior before any code existed. On the right track the test was written from the defective code, so the defect ships with a passing badge: the suite learned that zero-division returns 0 and now defends it. Same defect, same runner. The only variable is what the test was allowed to know.

The trap has three working parts, and this session springs each on purpose. First, the enshrined defect: a test asserting the buggy value — divide(1, 0) returns 0 — so the suite fails if anyone fixes the bug. Second, the self-confirming assertion: the code compared against itself, which passes for every implementation including unwritten ones. Third, the untested path, where deletions go unnoticed. One preprint study of 204,673 test files puts numbers on this shape: agents beat humans on edge-case variety (0.62 vs 0.32) and null-safety checks (13.40% vs 8.3%), trail slightly on assertion strength (85.37% vs 88.1%), and carry higher flakiness risk (0.41 vs 0.30) — thoroughness without hermeticity, a lack of "environmental awareness" in the authors' framing. Read it as a preprint, not a verdict: one dataset, one method, version 1.

Practitioner guidance converges on the same loop. Write the tests yourself — or co-write and review every assertion, asking of each: if the implementation were subtly wrong, would this fail? Confirm it fails for the right reason, hand the agent the failing test as the requirement rather than the prose around it, let it iterate to green hands-off, then review the diff against the test. The three-to-five contract assertions that define the feature must not be delegated; the agent earns the boundary cases afterward without touching them. Split the roles harder and the tautology dies structurally: one agent writes tests and cannot edit source, another implements and cannot edit tests.

iii.Proof you can replay · command plus output, everywhere

The standing rule fits on one line — save it verbatim in step 4: never "done" without the command and its output. A green suite proves the code satisfies the assertions; it does not prove the feature works, the server boots, or the page renders. So the agent exercises what it built: start the server in the background, probe the API it just created, paste the exchange. Manual probes routinely find bugs the suite missed, because suites check assertions while probes check behavior. The resulting document — command, output, verdict, next probe — is the demo: evidence assembled as it happens, not narrated afterward.

In the browser the same rule becomes per-action evidence. A trace records every step with its screenshot, DOM snapshot, network calls, and console output attached to the action timeline, reviewable without reading code. Four evidence types carry a session; each doubles as a checkable with one question — what change would make this turn red?

Tooling choice here is a token budget, not a loyalty test. The CLI path keeps browser control in discrete shell commands and never forces page data into the model — one third-party measurement put the awareness cost at 68 tokens for the skill description against roughly 3.6k for the MCP tool schema, with the sample task at 16% full success on the CLI versus 18% partial on MCP — success rates, not context share. Fence those digits: one hands-on comparison, one task, one agent — direction, not benchmark. The MCP path earns its keep where continuous context beats token cost: logged-in multi-step flows, exploratory automation, self-healing scripts, long-running agents. Record traces on the first retry of failed tests so every failure arrives with evidence attached, and open them where they load locally without transmitting data.

Where no boolean fits, evals-lite carries the same discipline one rung up. A task with defined inputs and success criteria, a grader scoring the outcome, trials run more than once because single runs lie — a handful of graded examples beat vibes every time. Start with tasks drawn from real failures, write each so two experts would reach the same verdict, and maintain the suite like tests: capability evals that start near zero and climb, regression evals near one hundred percent that guard the climb. Above all, read the transcripts, not the aggregates — only the transcript tells you whether the agent erred or the grader rejected a valid solution.

The conformance trick is the one-line version of everything above: build the passing suite against several independent implementations first, then implement yours against the suite. One worked example built file-upload tests that passed on six web frameworks, then grew the seventh implementation under them.

Beyond this build

The pattern ports anywhere an agent's word must become checkable fact: migrations (row counts before and after, pasted), documentation (every command executed fresh, outputs pasted), model upgrades (the eval suite re-run, deltas logged). It breaks down where observation is expensive — flaky end-to-end suites, paid calls per trial, hardware-bound runs — and there the answer is fewer, harder trials over hermetic unit tests, never belief on credit.
