§1

The repo you didn't write

Every technique so far in Part III assumed canvas you controlled. Real careers are spent somewhere else: inside codebases that existed before you arrived, with years of decisions folded into filenames, half-documented conventions, and couplings nobody remembers making. Practitioners call this brownfield — built-on land, as opposed to empty greenfield — and agents change its difficulty unevenly. An agent reads faster than you ever will and does not tire. But it also arrives with zero inherited intuition: no memory of the incident that made the retry logic so paranoid, no feel for which of the four similarly-named modules is the live one.

The hard constraint underneath everything in this chapter is arithmetic. A frontier working context window holds roughly 200,000 tokens at best — the budget Chapter 05 metered; the raw source of even a 400-file repository typically exceeds what fits unfiltered. Nobody — not you, not the model — can hold the whole system in mind, and that gap is exactly why maps exist. Greenfield work hides this because the codebase grows alongside your understanding of it; brownfield puts you and the agent at the bottom of an existing mountain on day one. The craft is compression with judgment: build a small, ranked sketch of the territory, expand it deliberately where the change will land, and only then edit.

One move outranks everything else on inherited ground, and it costs nothing: branch before you brief. Create a working branch — or at minimum a commit of the current state — before any agent touches the code. Every other safety move in this chapter is reversible only because of that baseline: a bad agent run becomes a throwaway branch you delete, not a wound you excavate from your working tree. Fold pinning into the same beat: before any editing, have the agent write characterization tests around the code you're about to change, so the suite — not your memory — judges whether behavior moved.

§2

Understand before you edit

The tool-agnostic discipline has four phases, and the documentation leads with a precondition rather than a step: give the agent a way to verify its work — a test command, a build, a script whose exit code doesn't lie — before asking for any change. Then: Explore: read-only investigation — find the files involved, follow the references, locate the tests pinning current behavior. Plan: write the intended change as a diff-shaped proposal — which files, which functions, what stays untouched — and check it against what exploration found. Implement: only now touch anything, smallest change first, checked against that verification harness immediately. Commit: a reviewed diff lands as a commit on your baseline branch — the run ends saved, not left dangling in a working tree. Official best-practices documentation for agentic harnesses encodes exactly this explore-plan-implement-commit arc for unfamiliar codebases, leading with the verify-first rule and including delegating investigation to subagents so the main session's context stays clean for the change itself.

The documented anti-pattern is just as instructive: infinite exploration — the session where the agent keeps reading, more files, more grep hits, another layer of indirection, and never commits to a plan, because "understand everything" was silently treated as the goal. You saw this loop's cousin in Chapter 01: a goal with no detectable finish line wanders. In brownfield work the wander wears a respectable disguise (it looks like diligence), so timebox it: exploration ends when you can state the plan, not when curiosity runs out.

§3

Maps of big repos: ranked sketches

If the whole repo cannot fit in context, what does? Every serious answer is some version of a repo map: a compressed outline of many files at once, spending its small token budget where visibility pays most. The reference implementation is aider's, worth knowing mechanically because the idea transfers to any harness. Aider parses every source file with tree-sitter to extract symbol definitions and references, builds a graph of which symbols refer to which, and ranks files by importance — files referenced from many places, and the entry points that anchor reference chains, rise; lonely leaf utilities sink. Then it greedily packs the highest-ranked files into a compact tree of paths and signatures, sized by a token budget set with --map-tokens. The founding writeup frames why bluntly: coding tasks need the model to find the right code, relate it to the rest, and change it — and finding-and-relating across a huge repo is what eats context budgets alive.

warning

Confident edits into unexplored code are how brownfield burns. The dangerous failures are not syntax errors — they are changes that compile, demo well, and violate a contract the agent never saw: an unmapped test suite, a second call site, a duplicate constant with different values. If the plan doesn't say where behavior is pinned, the edit isn't ready.

§4

A vocabulary for touching nothing

Brownfield safety has a shared vocabulary older than agents: the refactoring catalog. Fowler's refactoring.com catalogues named, behavior-preserving moves — Extract Function, Inline Variable, Move Method — each defined so applying it cannot change what the program does. This matters mechanically for agents, not just aesthetically: "extract the tax computation into a function, then change the extracted function" decomposes one risky edit into a provably safe move followed by a tiny obvious one. Naming catalog moves in your plan gives the agent a constraint it can execute mechanically — and gives you a review lens: every step should be individually verifiable as does-the-same-thing.

§5

Make the codebase legible to machines

Some codebases are simply easier for agents to work in, and the properties are knowable in advance. Ronacher's field analysis of agent ergonomics highlights local reasoning — files that make sense without holding the whole system in your head — grep-ability, distinctive names that search cleanly, and treating aliasing and indirection as refactor priorities precisely because they defeat an agent's ability to trace what calls what. Note the inversion from older advice: cleverness a patient human could eventually untangle loses to boring directness, because the agent's primary senses are search and local reading.

Conventions do the same work at team scale. From Willison's practitioner notes: the first person to use Redis in a codebase must do it perfectly — their pattern becomes the template every later contributor, human or agent, copies. Agents amplify whatever convention they find: a clean precedent reproduces cleanly, a rotten one reproduces fast. When you inherit a repo, find the exemplar module — the one done right — and point the agent at it explicitly ("follow the patterns in payments/refunds.js"); that steers quality more cheaply than any rule list.

tip

Before any brownfield edit, make the agent write a map of the neighborhood: entry points, hub files, where tests live, what looks dead. One prompt, zero diffs — and you hold exactly the artifact this chapter has been simulating. Review the map before the plan: errors there are cheap; errors downstream are diffs.

§6

Specs on inherited ground

Spec-driven development (Chapter 06) sounds like a greenfield luxury — write intent first, generate from it — but its tooling has an explicit track for established code. Spec Kit's official guide for existing projects walks through adopting specification-first workflows on a living codebase: characterize current behavior first, let the spec describe the delta, and use the constitution to encode house rules the generator must respect. Community practice goes further: in the project's issue tracker, practitioners describe reverse-engineering a constitution from an inherited codebase — mining the implicit rules out of the code and writing them down before generating anything. Flagged honestly: that second item is a community signal from an issue thread closed since this chapter's 2026-08-26 fact-check — closure is housekeeping, not endorsement, and its content still supports the point; a lead worth reading, not official doctrine.

Does it work at enterprise scale? One published case study from EPAM ran spec-kit phases against a legacy portal and argues the phases pay for themselves through compounding: if each phase catches errors slightly better than passing them forward, five phases multiply — their illustration is a ~0.8-to-the-fifth shrink in carried-forward defects, justifying per-phase review gates over one final review. Read that with the badge in view: EPAM is a consultancy, the venue is vendor-adjacent, and it reports a single-project sample. Directionally useful, not proof.

§7

Where this lands in your builds

The agent-cost-compass stayed small by design: one bounded question, one session, a handful of files — greenfield conditions all the way down, which is why brownfield skills could wait until now. They activate the day you inherit something bigger than a weekend: map, neighborhood sketch, plan, surgical diff becomes the default opening move.

The next build meets brownfield from the outside. The quiz-forge content pipeline doesn't invent its subject matter; it touches the existing NCERT chapter structure — a real external artifact with its own conventions, numbering, and edge cases that we must map and respect rather than "fix." Same discipline, foreign territory: understand the structure before generating against it.

Self-check

Why do entry points and hub files survive a shrinking map budget first?

Because the map is graph-ranked: files referenced from many places (hubs) and the anchors where execution starts (entry points) carry the most relational information per token. Leaf files reference little and are referenced by few, so dropping them loses the least context. That's aider's documented ranking logic, and the widget mimics it.

Describe the "classic brownfield failure" the widget predicts, and the map knowledge that prevents it.

The edit lands cleanly on the file the agent could see, quick checks pass — and a test file the agent never mapped breaks later, because the behavior contract existed outside its visibility. Prevention: a budget (or an explicit instruction) that keeps the spec and the truth-source file on the map, plus a plan that names where behavior is pinned before any edit.

When is a repo map the wrong tool — what does it systematically miss?

Maps rank symbol references; coupling that lives outside symbols — configuration files, data shapes, environment variables, side effects at import time — ranks poorly or invisibly. A repo can be fully "mapped" while the change breaks on a YAML flag. Pair maps with runtime verification: run the thing, don't just read the tree.

Beyond this build

Legacy migrations. The same arc scales up: map the neighborhood, then migrate module-by-module, each step behavior-preserving. Migrations fail when steps quietly change behavior; they succeed when every commit provably doesn't.

Dependency upgrades at scale. A major-version bump across fifty files is a brownfield problem wearing a version-number costume: map the call sites (grep-ability pays), plan per-site mechanical transforms, verify against pinned behavior. Agents excel at the per-site transform and need your map for the scope.

Wrap vs rewrite. For hostile legacy code the standing question: encapsulate it behind a clean interface and starve it, or rebuild fresh and cut over. Maps inform the choice — dense inbound references argue for wrapping; a small, isolated, badly understood core is sometimes cheaper to rewrite behind tests. Neither option excuses skipping the map.

Where it breaks down. Graph-ranked maps assume coupling lives in imports and references. Repos glued together by runtime config, database schema, or stringly-typed dispatch will map confidently and wrongly. Treat every map as a hypothesis with a budget — and keep the verify ritual from Chapter 01 attached to every diff, forever.
