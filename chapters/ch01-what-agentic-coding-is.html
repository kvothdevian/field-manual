Chapter 01 · What agentic coding actually is

After this chapter you can explain what a coding agent really is — model, harness, loop — run your first session without getting burned, and name the moments when reaching for an agent is simply the wrong move.

facts checked as of 2026-08-25

The hype flattened the language. "The AI built my app" can mean four different things: a chatbot answered while a human typed every change, an autocomplete guessed lines, a scripted pipeline transformed text, or an agent genuinely acted — read the repo, ran the tests, edited files, retried. Those are not shades of the same thing. This chapter builds the mental model everything else in this book sits on.

Three parts, one machine

Strip the marketing and every coding agent has three pieces.

The model is the language model itself — a system that predicts likely text, one token at a time. It has no hands. It cannot open a file, run a command, or remember yesterday. Left alone, it produces text and stops.

The harness is the program wrapped around the model. You never talk to a raw model; you talk to a harness that injects a system prompt you didn't write, hands the model tools — read this file, edit that function, run this command — enforces permission gates, manages the transcript so the model appears to remember the session, and feeds tool output back into the conversation. Practitioners describe a coding agent as exactly this: a harness wrapping a language model with invisible prompts and callable tools, where the ability to execute code is the defining capability. Two people using the identical model through different harnesses will have wildly different experiences — the harness is most of what you experience as "the product."

The loop is what makes it agentic. The working definition this book adopts: an agent is a language model running tools in a loop, toward a goal, bounded by a stopping condition. The model proposes an action, the harness executes it, the result feeds back in, and the wheel turns again — until the goal is met, the agent stalls, or the budget runs out. Remove the loop and you have a chatbot. A chatbot answers; an agent acts.

Notice what is missing from that loop: magic. The agent is not thinking in any deep sense. Each pass, it looks at everything in its transcript and predicts a next action. The craft of this entire book is shaping what the loop can see, what it may touch, and how it knows it is finished.

tip

Write the stopping condition before you write the goal. "Make the login page work" is a wish; "make these three tests pass without touching any other file" is a stopping condition. Clear success criteria are the highest-leverage habit in agentic work — trial-and-error loops need a finish line they can actually detect, and vague goals are how loops wander.

What makes it agentic — and when to skip it entirely

An agentic coding session differs from chatting with a bot in three concrete ways: the agent reads your actual files, runs real commands, and iterates on its own output without waiting for you between steps. Official documentation for leading harnesses is blunt that this is a different working relationship, not a faster chat window — you manage it more than converse.

There is also a distinction practitioners lean on constantly. A workflow is ordinary code orchestrating a model through steps a human already understands: summarize this, classify that, format the result. An agent is the model directing its own process, choosing which tools to run and when. The canonical guidance from Anthropic's effective-agents essay: start with the simplest thing that could possibly work, and reach for an agent only when the task genuinely needs flexible, open-ended execution — agents trade predictability for flexibility, cost more in latency and tokens, and compound errors along the way. Add complexity only when measurements say you must.

Say no to the agent when:

  • the steps are already known — a script or workflow is cheaper, faster, and cannot improvise surprises;
  • latency or cost budgets are tight — a loop of model calls is expensive by construction;
  • errors compound dangerously — anything irreversible on live systems belongs behind a sandbox and guardrails first;
  • you cannot state what "done" looks like — an agent with no success criterion cannot stop honestly, and neither can you verify it.
warning

Autonomy amplifies whatever it touches, including mistakes. Field reports describe agents that skipped permission prompts, stalled on slow tools, or wandered when a refactor exceeded their capacity — and the security story is worse: a rogue agent with shell access is a classic injection target. Treat any "skip approvals" flag as radioactive outside a disposable, sandboxed environment. Guardrails are part of the design, not an optional extra.

Three classic failure modes

These recur so reliably across teams and harnesses that learning to spot them by name is worth the price of this chapter.

Failure one: the kitchen-sink session. Five features go into one endless conversation. Context fills up, quality sags, the agent contradicts decisions it made an hour ago, and nobody can untangle the diff afterward. Official best-practices docs warn against exactly this shape. Fix: one goal per session, and treat a fresh start as cheap — it usually beats rescuing a bloated thread.

Failure two: the trust-then-verify gap. The output reads plausibly, so nobody reads the diff, nobody runs the proof, and a subtly broken change merges. Even careful practitioners admit the drift: as sessions get longer, reviewing every line erodes — but accountability stays human no matter what the tooling implies. Plausible is not correct. Fix: a verify ritual you never skip.

Failure three: the infinite wander. The agent re-reads the same files, tries adjacent fixes, stalls on slow tools, never converges. That is the signature of a goal too vague to detect progress, or a refactor bigger than one sitting. Fix: timebox the loop, narrow the goal, restart clean instead of nursing a doomed attempt.

Worth knowing alongside those three: instruction and memory files that grow unbounded quietly poison later sessions, and permission-skipping turns small mistakes into big ones. Both recur across field notes; both are habits, not bugs.

An honest word about speed

Before you assume agents make everyone faster, meet the most uncomfortable result in the field. In 2025 the independent nonprofit METR ran a randomized controlled trial: experienced open-source developers, real issues in repos they knew well, early-2025 agentic tools. Participants predicted a 24% speedup. After finishing, they believed they had achieved about 20%. Measured reality: the group using AI took roughly 19% longer.

+24%speedup participants predicted
+20%speedup they believed afterward
−19%measured reality · slower with ai

Read that honestly, in both directions: one narrow setting, early-generation tools, and follow-up work suggests newer models help more — do not generalize it into "agents are a scam." The durable lesson stands anyway: your feeling of speed is not data. Nobody in that study sensed a slowdown. Measure your own throughput occasionally — timers, commit history, boring spreadsheets — and update on evidence, not vibes. This book will keep asking you to.

Vibe coding vs agentic engineering: pick your words carefully

In February 2025 Andrej Karpathy described a new style he called vibe coding. The definition this book relies on is anchored not on the fragile original post but on Simon Willison's definitional essay, which documents the coinage: fully give in to the vibes, accept all diffs, stop reading them entirely, forget the code even exists — fun for throwaway weekend projects, explicitly not for serious work. The phrase escaped its cage almost immediately; headlines began using "vibe coding" for all AI-assisted programming, muddying a useful boundary.

Simon Willison drew the line back where it belonged: vibe coding is that specific mode where you accept output without reviewing it — and his golden rule is that you can't commit what you can't explain. Everyone doing serious work with these tools was never vibe coding; they were doing AI-assisted engineering with the review step intact. Later attempts at vocabulary settled the matter: Willison proposed "vibe engineering" in October 2025, then conceded in a February 2026 update that "agentic engineering" won the naming contest — a term Karpathy himself endorsed, as reported by The New Stack: orchestration of agents with oversight and no compromise on quality. That is the term this book uses, and the standard it holds you to: orchestrate, supervise, verify.

Where this lands in your build

The book's threaded projects start in the next chapter with a harness choice, and the first build — a small agent-cost-compass that turns pricing pages into a decision table — is deliberately tiny. One bounded question, one agent session, a written stopping condition, a verify step before anything merges. That is Chapter 01 compressed into an afternoon: the inner loop does the typing, the outer loop keeps you honest.

Try it yourself

  1. Exact-click checkpoint. Open anthropic.com/research/building-effective-agents, scroll to the workflows-vs-agents discussion, and copy its one-line description of an agent into your notes. Then sort three real chores from your life into two columns — "workflow would do" and "genuinely needs an agent" — writing the success criterion next to each.
  2. Break it on purpose. Take the second diagram above and delete its verify step on paper. Write down two concrete ways a wrong diff ships to production unnoticed. Check your predictions against failure mode two — the trust-then-verify gap is that exact diagram, amputated.
  3. Ship-sized task. Draft the stopping condition and the verify step for one real task you intend to hand an agent during the first build — one sentence each, both falsifiable ("these tests pass," "this table renders"). Keep them; you will paste them into a real session next chapter.

Self-check

In one breath: what is the difference between the model and the harness?

The model predicts text and can do nothing else. The harness is the program around it — system prompts, tools, permissions, transcript management — that turns prediction into action. Same model, different harness, completely different experience.

Name the three classic failure modes and one fix for each.

Kitchen-sink session → one goal per session, restart fresh. Trust-then-verify gap → a verify ritual you never skip (run tests, read the diff). Infinite wander → timebox the loop, narrow the goal, restart clean instead of rescuing.

A friend says "agents made me 40% faster." What do you ask before believing it?

Measured how? Self-timed feelings are exactly what the METR trial punctured — participants believed they were 20% faster while measuring 19% slower. Ask for the comparison condition (with vs without, same tasks), who timed it, and whether the logs agree with the memory.

Beyond this build

Where else the pattern applies. The loop — model, tools, stopping condition, verification — is not coding-specific. Data cleanup, research digests, ops triage, spreadsheet wrangling: anywhere a machine can act on tools and you can check the result, the same shape works. Change the tool belt, keep the discipline.

Other tools, same anatomy. Harnesses differ mainly in surface and defaults — terminal-first, IDE extensions, desktop apps, cloud agents that run in the background — while the underlying loop stays identical. What varies that matters: which tools are exposed, how aggressively approvals are enforced, how much context survives between sessions. The next chapter maps that landscape properly.

Where it breaks down. Agents struggle when you cannot verify the outcome (pure taste calls), when mistakes are irreversible on live systems without a sandbox, when a huge unfamiliar codebase offers no tests or breadcrumbs to steer by, and whenever accountability is yours but oversight is absent. If you cannot state what done means, you are not ready to delegate it — to an agent or to anyone.
