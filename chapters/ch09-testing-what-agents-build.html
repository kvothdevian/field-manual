Chapter 09 · Testing what agents build

Promise: after this chapter you can verify agent output like a skeptical QA lead — ordering tests so they can actually fail, demanding browser evidence for UI, and running review gates you can execute without reading a line of code.

facts checked as of 2026-08-26 · every claim below traces to the book's source ledger

Agent output arrives pre-green. The diff looks clean, the demo works on the happy path, the summary says done. The trust-then-verify gap from Chapter 01 is widest exactly here, and this chapter is the closing move: the QA-lead habit of assuming nothing works until evidence says so. Three skills make up the habit — put the test in the right order, collect evidence instead of assurances, and build gates shallow enough that anyone can operate them.

Verification is an ordering problem

A test is an instruction to the loop. Chapter 06 introduced tests as the steering wheel; what it could only name in passing, this chapter makes you feel: the wheel only steers if it was bolted on before the car moved. Write the test first and it is a specification — the code must come to it. Write the test after and it is a biography — it can only describe what the code already does, misreadings included.

That second path has a name: the tautology trap. Field synthesis of agentic development datasets found that tests written after the code tend to encode the model's own misreadings, producing suites that pass while the behavior is wrong — the test agrees with the code because it learned correctness from the code. Practitioner defenses exist (review contract tests as specification, audit for hermeticity), but the cheapest defense is structural and costs one sentence of prompt. Willison's red-green guide reduces it to exactly that: write a failing test first, confirm it fails, then make it pass. The confirmed failure is the entire point — it is proof the test can fail, which is what separates an instrument from a decoration.

The same skepticism applies to the agent's own reports. An agent that ends with "the feature works" has asserted; an agent that boots the server, hits the endpoint, and pastes the transcript has exercised. Practitioner rule from the field: agents must exercise what they build and show the evidence, not declare success — and the corollary for you is that "it passed" is a claim, while a captured command and its output are a fact.

The experiment: same feature, two orders

Judge the ordering argument yourself. Below, two teams build the identical tiny feature: a page that divides two inputs and shows the result. Unknown to both, one of three defects rides along — a division-by-zero leaking raw Infinity, a negative input quietly losing its sign, or floating-point garbage in the decimals. Which defect is drawn is randomized each round, shuffled so repeated plays cover all three. Track A codes first and writes tests afterward. Track B writes the failing test first. Press both through, watch the same bug meet two different workflows, and let the scoreboard keep the honest accounting: bugs caught per minute of verification, across as many rounds as you play.

Play at least three rounds so the shuffle deals you all three defects. Then read the totals the way a QA lead would. Track A posts the fastest verification time in the building and a permanently perfect green suite — and a bug-catching rate of zero, forever, because a test that merely restates the code cannot fail. Its green light certifies agreement, not correctness: 1 ÷ 0 shipping as "Infinity — verified ✓" is the tautology trap made visible. Track B looks slower on paper and catches every defect at step one, because the red run happens before the code exists and names the violation in the spec's own words. That asymmetry is the whole chapter: verification time buys nothing without sensitivity, and sensitivity comes from order.

tip

Make the agent write the check before the fix. One line of prompt does it: "write a failing test first, confirm it fails, then make it pass." The confirmation step is non-negotiable — an unconfirmed red is a guess, a confirmed red is a measurement.

warning

Green ≠ correct. A test that cannot fail is decoration. Before trusting any suite — especially one the agent wrote after the code — ask the only question that matters: what change would make this turn red? If the honest answer is "none," you are looking at Track A.

Browser evidence for UI: the trace as a review gate

Unit tests argue about logic; interfaces need evidence a human can eyeball. For UI work, the strongest non-coder-reviewable artifact in current practice is the browser trace: Playwright's trace viewer records a screenshot, DOM snapshot, network activity and console output for every action in a run, replayable step by step. You do not read the code to review the feature — you open the trace and watch what actually happened. That is a gate a non-coder can operate: did the right request fire, did the right pixels render, did the console stay quiet?

operate the gate · two commands · per playwright.dev/docs/trace-viewer

Record a trace: run npx playwright test --trace on — or set trace: 'on' in your Playwright Test configuration.

Open it: run npx playwright show-trace path/to/trace.zip, or drag the zip file into trace.playwright.dev.

Getting that evidence through an agent involves one genuine tradeoff, and Microsoft documents both sides of it. The @playwright/cli route is token-cheap: it deliberately does not push page data, accessibility trees, or tool schemas into the model's context, and it ships a show --annotate dashboard built for UI review. The Playwright MCP server takes the opposite deal — heavier context load in exchange for continuous, stateful back-and-forth with the live page across many turns. An independent hands-on comparison measured the difference at roughly 68 tokens of skill description versus about 3.6k tokens of loaded schema — treat those digits as one third-party measurement, not gospel, but the direction is stated plainly in Microsoft's own repos: CLI when you want cheap bursts of evidence, MCP when a long interactive session genuinely needs shared page state. For review gates, bursts win most of the time. Performance checks ride the same rails: "check the performance of this URL" through a browser-driving agent produces trace-backed timing evidence as an acceptance artifact.

Evals-lite: grading what assertions can't

Some qualities refuse to become booleans — "is this summary faithful," "does this reply sound right." The lightweight version of an eval, per Anthropic's engineering team, needs exactly three parts: a task, one or more graders, and a judged outcome. Their operating advice reads like QA folklore distilled: grade real outcomes rather than proxy signals, read the transcripts yourself instead of trusting aggregate scores, and maintain the suite like any other test asset. Chapter 06 covered the full ladder and the judge-alignment discipline; here, take the floor: even five graded examples beat vibes, because the grader forces you to write down what "good" means before the agent touches anything.

Two practitioner moves worth stealing

The conformance-suite trick: when several implementations must agree, write the shared passing suite first — every implementation, human or agent, then earns green by conforming to it. Willison documents the pattern with a worked example; it converts "please match the existing behavior" from a hope into a gate.

The evidence mandate: from the same field notes, "tests are effectively free now… no longer optional" — the marginal cost of asking the agent to prove its work has collapsed, so the excuse not to has collapsed with it. Bake it into your standing prompts: show me the command and its output.

Where this lands in your build

The compass build already runs this chapter in miniature. Its npm run verify is nine pinned assertions — hand-checked pricing calculations, including deliberately asymmetric cases — and the milestone log records math passing 9/9, independently re-run during review. Nobody trusted that result by reading calculator code; the reviewer ran one command and read nine lines of pass/fail. That is a review gate a non-coder operates, and Build 2 extends the same shape from math to facts: quiz-forge's batch gates require every generated question to be read against the actual textbook before it ships. Same skeleton in all three places — checks that can fail, executed by someone who did not write the thing being checked. When Chapter 12 wires CI pipelines, these are the commands that become merge-blocking gates; the habit you build now is the config you will paste later.

Try it yourself

  1. Exact-click checkpoint. Play four rounds of the lab above. Before each round, predict which defect the shuffle holds and which track will surface it. After round 4, read the totals line aloud: what is Track A's bugs-per-minute, and would you hire that number?
  2. Break it on purpose. Open playwright.dev/docs/trace-viewer and find the list of what a trace records per action. Write down the four evidence types, then answer: which one would have exposed the Infinity bug from the lab without reading any code?
  3. Ship-sized task. In your next real agent session, paste Willison's one-liner — "write a failing test first, confirm it fails, then make it pass" — and add the evidence mandate: "end by showing the test run's command and output." Compare how much you trusted this session's result versus last session's "done!".

Self-check

Why does Track A's suite stay green while the page is wrong?

The tests were written after the code and read back off it, so they encode whatever the code does — including the misreading. The suite proves the code agrees with itself, which is a tautology, not a verification. Only a check derived from an independent source (the spec) can disagree with the code, and disagreement is what catching bugs means.

What does the confirmed red buy that a passing test never can?

Proof of sensitivity. A confirmed failing test demonstrates it detects the missing behavior before any code exists; the later green then measures real progress. A test that starts green has demonstrated nothing except that it matches whatever is already there.

Name one situation where clicking manually beats writing automation.

One-shot or heavily aesthetic work — a landing page you will rebuild next month, a visual taste call, first exploratory contact with a feature. If the check would outlive the thing it checks, or the judgment is yours alone, spend the click, not the harness. Automation earns its keep on behavior that must keep working after today.

Beyond this build

Pipelines. A test only steers while someone runs it. Chapter 12 promotes these checks to CI gates — run automatically on every proposed change, blocking merges — which is where the compass verify script and the quiz-forge content lints are headed. The ordering lesson survives the promotion unchanged: a pipeline full of tautologies blocks nothing.

Property-based testing. Instead of pinning example inputs, you state a property — "sign is preserved," "result times divisor rounds back to the dividend" — and a generator throws hundreds of random cases at it. It pairs naturally with agents: the property is short enough to specify in a prompt, and the machine does the tedious case enumeration.

Where it breaks down. Suites rot: behavior changes, tests fossilize, and a green legacy suite can certify yesterday's product. Fuzzy qualities resist assertion — that is what evals-lite is for, and why graders need periodic re-alignment against human judgment. And the deepest limit is the spec itself: tests inherit the spec's blind spots, so a miswritten requirement passes forever. Verification amplifies the quality of your intent; it cannot substitute for it.
