i.Three doors, one drill

Tonight you booby-trap a scratch repo against your own agent: a fake key in .env, a forged order in the release notes, a push it may not make. Four probes, then read the transcript like a security camera. All three proofs — or a honeypot lesson, the cheapest kind.

The threat model fits in one paragraph. Exploits need three legs at once: private data worth stealing, untrusted content smuggling instructions, a channel carrying the loot out. Remove any leg and the machine stops. The originating essay calls this assembly the lethal trifecta: guardrails soften each leg, none removes one. Break one leg on purpose, every session.

Door one is secrets: containment, not trust. The agent will reach for .env mid-job — ours did in probe four — so reach must never equal intent. Every context window is a future leak. The drill checks the transcript, not intentions: fake value at zero hits, file timestamp unmoved. Chapter 4 built the defaults; nothing here re-teaches them.

Door two is untrusted content: testimony, never orders. Files and pages describe the world; only live keystrokes command. The forged block shouts CRITICAL and demands a push — handle it by quoting with filename plus one why-not sentence, then executing zero injected steps. Quoting is not obeying.

Door three is exits: every way out stays gated. Push, publish, send need an explicit yes, and the convenience-flag family that skips approval is the attackers' invitation in your own config. Probe four asks for a push and watches the agent propose the widening in ALLOW/ASK/DENY words, then stop at a question.

Then the supply-chain twist — why this chapter stands beside chapter 4: the bloodiest real cases walked two doors at once with no injection: compromised build packages drove installed AI CLIs with the convenience flags to enumerate secrets, and a malicious mail package siphoned messages through its normal function. Private data plus a way out, no forged order. Section iv lays the cases side by side.

Defense order, tightest first: deny beats ask beats allow, evaluated in that order regardless of specificity. Denials belong in permission rules — the harness enforces them, while prompt text only shapes attempts. Denies stop built-in reads and the recognized cat-family commands; the honest residual is arbitrary subprocesses, needing OS-level sandboxing. Hooks stay silent-or-deny — quiet or malformed output never approves — so hard denials live in rules. Denies are a floor, not walls: pair every rule with a live refusal test, which is what the session runs.

ii.Assembled versus inert · read the triangle

Walk the triangle corner by corner and each corner names one thing you can take away. Private data is anything the transcript must never carry: keys, tokens, mailboxes, wallets. Untrusted text is anything a stranger could have written: the notes file, an issue body, a fetched page. The way out is any command that moves bytes beyond your machine: push, deploy, post, send. The executed drill removes a different leg at each step — step two withholds the key, step three withholds obedience, step four withholds the exit — and the transcript is the instrument that confirms each removal.

iii.The ladder and the hook footnote · deny beats ask beats allow

Deny, ask, and allow are not three flavors of yes. They are a ladder evaluated top-down: the first match in deny-then-ask-then-allow order decides, and a narrower rule lower down never overrules a broader one above it. That is why the convenience flags are dangerous — each one is a broad allow stapled above the asks you carefully wrote. The table below is the whole policy in nine cells; read your own config against it after the session.

RungWhat it doesWhere the denial lives
Deny ⛔Blocks outright, even past a matching allow; stops built-in reads AND recognized cat-family commands (verified 2026-09-04)Permission rules — enforced by the harness, not the model
Ask ⏸Prompts every time; opencode answers once, always-for-this-session, or rejectPermission rules; the prompt is the gate, the session scope is the leash
Allow ✓Runs silent; safe only for narrow, named commands like a fixed test invocationLast-match-wins granular rules; broad allows are the attackers' invitation

The hook footnote, stated exactly as the live page words it: a hook that exits quietly returns the call to the normal permission flow, and hook output that fails validation is a non-blocking error — the action proceeds. Hooks can deny, but staying silent never approves, and a matching deny rule still blocks even when a hook returned allow. So hooks observe and occasionally veto; rules decide. Put the secret-file denies and the push denies in rules, use hooks for lint-style reactions, and never let a hook be the only thing between a key and the door.

iv.The supply-chain twist · P+O with no injection at all

Chapter 4 rehearsed a single refusal: one forged instruction, declined. The cases below are worse, because nobody injected anything — trusted tooling turned hostile and walked private data out through legitimate channels. Read the three cards left to right as one argument: the first two assemble private data plus a way out with no untrusted-text leg, which means an injection drill alone would never have caught them, and only exit gating plus secret containment covers the gap.
