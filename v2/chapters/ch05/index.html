Context engineering

Audit what enters your agent's context, price it in tokens, cut a third of it without losing quality — and learn exactly when delegation pays and when it taxes.

60 min · scratch repo · needs ch04 · verified 2026-09-03

Briefing · 5 min · the finite budget

i.The attention budget

Context is a finite resource with diminishing returns, and the reason is architectural: every token attends to every other token, so attention stretches thin as windows grow — models lose focus the way people lose working memory. The field calls the degradation context rot: measured across eighteen frontier models, recall decays non-uniformly with input length even on trivial tasks, and distractors compound the damage. The engineering answer is one sentence that governs this whole session: find the smallest set of high-signal tokens that maximizes the chance of the outcome you want. Everything below is a technique for spending that budget well.

Know what you are spending it on. A session's context is an itemized bill: system prompt, memory files, skill descriptions (cheap until loaded — progressive disclosure), deferred tool schemas, every file read, every tool result. What survives compaction — the practice of summarizing a near-full window and restarting with the summary — is a second bill: decisions and bugs persist, raw tool outputs get discarded, recently touched files ride along. And the three long-horizon levers, named by the people who run agents at scale: compaction for conversational flow, structured note-taking for milestones, sub-agent architectures for parallel exploration that returns condensed summaries. Against them stands the canonical counterpoint, and you will feel it execute today: naive fan-out is fragile, because actions carry implicit decisions that don't survive the summary — share full traces where it matters, delegate where it pays.

The essay's sharpest operational idea deserves its own paragraph: just-in-time retrieval over pre-loading. Instead of stuffing everything the agent might need up front, maintain lightweight identifiers — file paths, stored queries, links — and let the agent pull data at runtime with tools. Claude Code works this way by design: memory files drop in naively, then glob and grep navigate just-in-time, bypassing stale indexes entirely. Metadata does quiet work here: a file named test_utils.py in tests/ means something different than the same name in src/, and timestamps proxy relevance. The tradeoff is honest: runtime exploration is slower than pre-computed retrieval and needs opinionated tooling (without guidance the agent chases dead ends), so the mature shape is hybrid — retrieve some up front for speed, explore autonomously at discretion. Your audit below will show which side of that hybrid your sessions live on.

ii.Audit your own context · 15 min · measured

Before changing anything, read the meter. opencode ships one: opencode stats reports sessions, messages, cost, and average plus median tokens per session. On this machine, mid-book: 168 sessions, 4,483 messages, $0.00 — and a median 356K tokens per session against a 2.6M average, which tells you the distribution is skewed by a few marathon sessions. That skew is the audit's first finding on almost every machine: a handful of bloated sessions dominate the budget.

Read the skew as a diagnosis, not trivia: a median far below the average means a few marathons ate most tokens, and marathons are almost always kitchen-sink sessions wearing a trench coat — five goals, one thread, context rotting since hour one. The session-01 fix applies before any technique in this chapter: split the marathon into one-goal sessions first, then optimize each. No compaction strategy rescues a session that should have been five sessions; the cheapest context engineering is a fresh start, and the stats readout tells you exactly which past sessions prove it.

Then inventory one live session's bill by hand. List what entered: the memory file (bytes on disk — divide by four for a rough token estimate), skill descriptions (one line each until loaded), the files read (bytes likewise), the tool results (usually the largest line). Price each segment, rank them, and write down the single largest consumer. The usual suspects are tool-result volume and overgrown memory files — and both have the same fix, which is the next step. Worked example from the lab that built this chapter: the slim session's bill was a 66-byte memory file (~15 tokens), two file reads (~100 tokens), and three short tool results (~200 tokens) — under 500 tokens of context to fix a bug. Then the trim pair repriced it: the same task on a 100-byte stopping-rule-only file (~25 tokens) with an identical outcome — the memory line of the bill cut 91% with zero quality movement. Two priced bills, one task, one conclusion you can defend: memory size moves the bill more than any other single lever on small tasks, because it loads first and colors everything after it.

2.Bloat vs slim — the A/B run

Goal: feel memory rot behaviorally. Same fixed task on a 66-byte memory file versus a 1,122-byte one stuffed with exactly the anti-patterns the literature warns about: laundry-list edge cases, contradictory style rules, fake lore, rhyming-commit mandates.

◆ slim run (66-byte AGENTS.md) · glob → read → edit → +1 −1 ◆ slim proof, verbatim: → 12 → "Proven: mul(3, 4) returns 12." One shot. ◆ bloated run (1,122-byte AGENTS.md) · glob → read → edit → +1 −1 ◆ bloated proof, verbatim: → "ZEBRA-7 12" — the junk codename inserted INTO the proof command Executed 2026-09-03, same prompt, same model, full logs retained outside the repo. Two honesties: the slim re-run globbed (first-move varies run to run — the earlier direct-read was luck, not law), and an earlier bloated run is VOID and excluded (dirty tree, my staging error — discarded runs stay discarded). Demonstrated effect: junk obedience (ZEBRA-7). Causality fenced: one clean pair shows correlation + mechanism, not proof — your re-runs decide.
⚠ If stuck

No behavioral difference? Good data, not failure — small models on tiny tasks are robust to bloat. Scale the junk (or the task) until something moves, and log where. The rot literature measures degradation on long inputs; your two-file repo may simply be below the threshold where it bites. And consider the alternative explanations honestly before claiming victory in either direction: single pairs don't separate bloat effects from model variance (re-run each side three times and compare distributions, not anecdotes), and a model that already knows the task pattern may bulldoze through junk that would sink it on unfamiliar work. Watch first-move variance specifically: our own slim runs opened with a direct read once and a glob the next time, same config — the opening move is sampling noise, and only patterns across re-runs (junk obeyed twice, proof shape thrice) graduate to findings. The A/B is a lens, not a verdict — its product is a priced observation plus a fenced causal claim, exactly the two lines in your verify box.

✓ Verify
  • Both traces logged with first-move, proof shape, and any junk obedience quoted
  • Causal claims fenced: observed vs proven, in writing

3.Trim — cut a third, prove it

Goal: the teach-test behavior itself: cut memory ≥30%, re-run the proof, show nothing broke. Stopping condition first: memory file smaller by a third or more, fixed task green, diff one file.

Replace the bloated memory file with one keeping only the stopping rule (~100 bytes vs 1,122 — a 91% cut, ~280→~25 tokens), then re-run the identical fixed-task prompt:

◆ trim: AGENTS.md 1,122B → 100B (91% cut) · re-run → edit +1 −1 ◆ trim proof, verbatim: → 12, no junk prefix, "Proof: mul(3, 4) → 12." Executed 2026-09-03. The junk obedience vanished with the junk: clean proof, no ZEBRA-7. Before/after priced: ~280 tokens of memory → ~25, identical task outcome. That pair — priced cut plus green re-run — is the ≥30% demonstration this session promised.
⚠ If stuck

Trim broke the task? You cut signal, not fat — restore from git, cut half as much, re-run. The verify box below is the judge: green proof plus smaller bill, or it doesn't count. Never "feel" a trim; price it. And run the restore-and-halve protocol when a cut fails twice: restore fully, confirm green, then cut a quarter of what you cut before. Binary search beats guessing — two halvings locate the line between fat and signal faster than any amount of staring at the file. Log every attempt as bill-before, bill-after, proof result; three logged attempts make a trim history worth keeping, and the history is what stops the next session from re-trimming what you already proved load-bearing.

✓ Verify
  • Before/after byte counts logged with token estimates; cut ≥30%
  • Fixed task re-run green on the trimmed config, diff one file

4.Delegate — price the subagent

Goal: a measured answer to "when does delegation pay?" Run an exploration through a subagent and make it price itself.

Explore this repo (AGENTS.md, mul.js, git log) using a delegated subagent for the exploration, then report: what you found, and roughly how many tokens the subagent used vs what a full read would cost. Keep the main response under 150 words.
◆ Explore subagent spawned ✓ · reported accurately — including committed-vs-working-tree state ◆ self-priced: ~1,500–2,000 tokens vs ~200–300 direct → 6–8x overhead here ◆ verdict (its own words): "justified only if the task were more complex" Executed 2026-09-03. The subagent was right: delegation on a tiny repo is pure overhead. That is the Cognition lesson with numbers attached — delegate where the exploration dwarfs the summary, never by default.
✓ Verify
  • Delegation ratio computed for your repo (subagent cost ÷ direct-read cost)
  • You can state the threshold where your delegation starts paying
⚠ If stuck

Agent won't delegate? Don't argue — delegation is architecture, not persuasion. Some harnesses need explicit subagent types or config; if yours won't, run the comparison manually (full read vs written summary) and price that instead. The ratio is the lesson, not the tool call.

Generalize the ratio before you forget it — worked illustration, not measurement: if a subagent burned 30,000 tokens to return 1,500, that would be 20x compression of what the main window never held. Ours measured 6–8x the other way (summary approaching exploration cost), and it rots when subtasks share hidden state the summary can't carry (the Cognition warning: conflicting-context workers producing fragile merges). The decision rule fits one line: delegate breadth (independent searches, parallel recon), never depth-with-shared-state. And price the summary itself — five simultaneous 1,500-token returns would park 7,500 tokens of other agents' conclusions in your "clean" main window. Fan-out has a budget too. Compute your break-even before delegating by habit: divide a typical exploration cost on your work by the summary size you accept, and delegate only above a ratio that beats your direct-read baseline with room to spare — rule of thumb, 3x measured, not hoped. Below that line, the subagent is ceremony; above it, leverage. The documented pattern to calibrate against is roughly 14x (6,100 tokens of recon returning 420); your work will differ, and now you know how to find your number.

5.Compact — the reader-run lever

Goal: watch a long session survive its own window. Compaction can't be forced headlessly with dignity, so this step runs in the TUI on your longest session: invoke /compact, then inspect what survived.

# in your longest opencode session: /compact # then ask: "summarize what you retained about this task in 5 bullets"

What should survive, per the documented semantics: architectural decisions, unresolved bugs, implementation details — plus the five most recently accessed files. What should die: raw tool outputs, redundant messages. Grade your compaction against that bar; if a decision vanished, your structured notes (NOTES.md habit, session 16) have a gap to fill. opencode exposes the continuation prompt as an experimental plugin hook for the day you want to tune it. And start the cheapest long-horizon habit tonight: a running NOTES.md where the agent records decisions as made — one line per decision, dated. Compaction then summarizes a window that already contains its own minutes, instead of reconstructing them from archaeology. Notes are how sessions survive their own summarization.

✓ Verify
  • Post-compaction summary graded against the survive/die bar; gaps logged
  • Rubric: every bullet tagged retained-decision, retained-bug, retained-detail, dropped-noise, or dropped-signal — four keeps and one honest loss is a healthy compaction
⚠ If stuck

Nothing to compact yet? Your sessions are short — that's a compliment to your session discipline (one goal per session compacts naturally). Borrow a marathon: export any long transcript and grade what you would keep vs cut before ever invoking /compact.

iv.The trim checklist · tonight's habit

End with the checklist that converts the audit into a routine. Run it whenever a session feels sluggish — sluggishness is usually context, not model. One, kill hungry tools: an MCP server that dumps schemas on load (the docs' own example: a GitHub server that "can easily exceed the context limit") gets disabled or glob-scoped before anything else. Two, slim memory: cut the file to conventions that changed a trace this month; move procedures into skills where bodies load on use. Three, canonical examples only: replace the laundry list of edge cases with diverse canonical ones — the essay's explicit guidance, and the exact anti-pattern the bloated run wore. Four, minimal toolsets: if you can't say definitively which tool handles a situation, neither can the agent — prune overlap. Five, clear tool results first: the lightest-touch compaction in existence is dropping raw results deep in history; whole summaries are the heavy machinery for when clearing isn't enough. Five cuts, ten minutes, one re-run to verify nothing broke. Log the bill before and after in identical units — bytes and estimated tokens, dated — or the trim never happened. That loop — audit, trim, verify — is context engineering as a practice rather than a chapter. Schedule it monthly alongside the limits-page ritual from session 03: contexts rot and prices move on the same clock, and one sitting maintains both.
