Session 10 · debugging discipline · opencode default

Debugging when it breaks

When the agent's second fix misses, stop the run: repro and failing test committed, code reverted, and a fresh session opened error-first.

70 min · scratch repo · needs ch06 · verified 2026-09-04

Briefing · 5 min · the sixty seconds after a break decide the evening

i.Two misses, then the hatch

A red test at 6 p.m. is a fifteen-minute job. The same red test at 11 p.m. — after nine speculative fixes and a context window full of failed approaches — is a lost evening. The difference is never the bug. It is the first sixty seconds after the break: recipe or theory, oracle or vibes, halving or wandering, hatch or grind. This session installs the sixty-second reflex.

Repro before theory, always. A repro recipe has four slots — input, command, expected, actual — and fits on an index card: basket [100, 50] with 10% discount, $20 promo, 10% tax; node check.js; want 126.5; got 128.7. Write it before anyone explains anything, then encode it as a failing test, because prose rots and assertions do not. Demand the root cause, never the suppression: a fix that silences the error while the wrong order still ships is a bomb moved to a darker room.

Halve, don't walk. Eight suspects need at most three midpoint tests (⌈log₂8⌉ = 3) against six linear ones — but only with an oracle that votes by exit code, an ordered history to halve, and deterministic verdicts. Miss any one and bisect lies: flaky tests name random culprits, squashed histories hide the seam, a missing oracle turns midpoints into opinions. Pin the repro first; halving multiplies a solid oracle, never substitutes for one.

Hatches are exits built before you need them. Rewind to a checkpoint instead of unpicking edits by hand. After two failed corrections, clear the thread and restart error-first — the context is polluted with approaches that do not work. Self-installed caps turn the rule into furniture: a correction counter on paper, a Stop hook that blocks a turn until a check passes (overridden after eight consecutive blocks, so the cap fails loudly). One log file, one fast loud loop, standing permission to abort a degraded session.

ii.The loop with exits · thrash has a number

Every debugging run is the same loop: attempt a fix, read the oracle, decide. What separates debugging from thrashing is not effort or skill — it is whether the loop has a counter and the counter has a gate. Without both, each miss feels like progress ("we ruled something out") while the context fills with dead approaches that the next attempt must wade through. The official guidance names the number plainly: after two failed corrections on the same issue, clear the session and write a better first prompt with what you learned. Two is not a metaphor. It is the gate in the figure below, and this chapter's session trips it on purpose.

Each exit answers a different failure. Rewind is cheapest when the code moved but the thinking was sound — restore conversation, code, or both to a checkpoint and retry the risky move knowing recovery is one menu away. The error-first restart is for polluted context: the thread now contains two wrong theories stated confidently, and every further correction negotiates with them. Clearing feels like losing work; it is actually deleting evidence that misleads. The Stop-hook gate is the deterministic cousin — a script that blocks the turn until the check passes, with the documented override after eight consecutive blocks so a wrong gate fails loudly instead of holding the run hostage. Aborting the degraded session is the last exit and the one beginners skip: compaction has fired, the model has forgotten the recipe, the log file contradicts the summary. Close it. The scratch repo below keeps every artifact, so no exit destroys information — that guarantee is what makes the exits cheap enough to actually use.

Two habits keep the loop honest between exits. First, one log file: every oracle run appends to the same place with its exit code, so "what did we try" is a file, not a memory. The practitioner advice behind this is blunt — log everything to one file, keep the feedback loop fast and loud, use defensive commands that fail visibly. Second, a fast loop: the oracle here runs in under a second, which means each midpoint and each miss costs a keystroke, not a coffee. Slow oracles invert the economics — when verification takes twenty minutes, speculative fixes look cheap by comparison, and the counter never gets consulted. If your oracle is slow, the debugging procedure starts one step earlier: make it fast first.

iii.Halve, don't walk · executed 2026-09-04

The bug in the scratch repo is a promo applied before the discount instead of after — a two-line swap committed as an innocent "refactor," followed by an unrelated shipping commit that buries it. Eight commits deep, the failing basket reads got 128.7, want 126.5. Reading all eight diffs would find it; halving finds it in three midpoint tests. The transcript below the session steps is quoted from the executed run: three midpoints, three exit-code verdicts, first-bad named, then hand-verified commit by commit and reset. Nothing in it was retyped.

The contract that makes it work lives in the bisect manual and fits in one sentence: the tested command exits 0 for good, 1–127 (except 125) for bad, 125 for "untestable, skip," and anything else aborts the whole session. That sentence is load-bearing. Exit 125 is how a revision that predates the oracle votes "present, not guilty" instead of failing loudly — early commits in this repo have no check.js at all, and without the skip rule the very first midpoint would convict an innocent commit. The manual's own examples keep the test script outside the repository for exactly this reason: checkout churn must never be able to touch the thing that judges the checkout. The wrapper here does the mapping — green passes 0 through, red passes 1 through, missing oracle becomes 125 — and the verdicts come from exit codes only, never from reading output.

◆ midpoint 1 · c4 discount support → oracle green (exit 0) · GOOD
◆ midpoint 2 · c6 promo-after-discount → oracle green (exit 0) · GOOD
◆ midpoint 3 · c7 refactor promo order → FAIL 128.7 vs 126.5 (exit 1) · BAD
◆ verdict: first-bad = c7 "refactor promo calculation order" · hand-verified c7 red / c6 green · bisect reset

Know where halving breaks, because it breaks silently. No oracle: verdicts become opinions and the search convicts at random — pin the repro first, as the briefing demands. No ordered history: a squashed import or a rewritten branch has no midpoints to test, and bisect will happily search a line that was never built. Nondeterministic verdicts: a flaky test votes differently on the same commit twice, and the "first bad" it names is fiction — quarantine the flake (fixed seed, pinned data, retried verdicts) before trusting the search. Each breakdown has the same shape: the procedure multiplies the oracle's authority, so a compromised oracle produces confident wrong answers. The hand-verification at the end — check out the accused commit, watch it fail; check out its parent, watch it pass — is not ceremony. It is the one verdict no automation casts for you.

iv.What stopping at two saves · the evidence bar

The thrash log is the cheapest horror story in this book. Miss one "fixed" the rounding and turned a one-line failure into two — including a previously green assertion now reading got 149, want 148.5. Miss two "fixed" the tax line and moved both failures sideways (147, 128). Neither miss touched the actual defect, both diffs looked industrious, and the correction counter is the only instrument that noticed. The pinned fix is a two-line swap that restores the order discount → promo → tax and turns the whole suite green. Small diffs are not the point — verdicts are — but notice the direction: every speculative edit made the evidence worse, and the revert made it legible again.

"Fixed" is an evidence bar, not a feeling. The practitioner rule behind it: the agent must exercise what it built — boot the server, curl the endpoint, run the suite — and show the output rather than assert success. Reviewing pasted output is faster than re-running verification yourself, and it is the only review that works for sessions you did not watch. Apply that bar to the hatch fix and it clears cleanly: the full suite printed green, the diff touched one file, the exit code was 0. Apply it to either miss and both fail on the spot — which is precisely why the misses had to be reverted rather than reasoned about. A red oracle ends discussion; that is what oracles are for.

None of this depends on a harness, which is why the chapter teaches it as a packaged procedure: recipe → oracle → halve → hatch, in that order, with the counter on paper where every run can see it. The packaged systematic-debugging skill in the wild says the same thing from the other direction — trace backward from the failure through the call stack toward the root instead of forward from theories toward symptoms. And the honest caveat rides along: production-trajectory forensics (normalizing agent runs, replaying failures as test artifacts) is sound synthesis, not independently reviewed research — useful scaffolding, cited as what it is. Procedures you can print beat discipline you have to remember, because at 11 p.m. nobody remembers anything.
