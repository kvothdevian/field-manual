Session 01 · orientation · opencode default

Your first agent session

Run a real coding-agent session in a scratch repo and end with one reviewed, verified change you fully understand — plus a stopping condition you will reuse forever.

45 min · scratch repo · beginner · verified 2026-09-03

Briefing · 5 min · the whole mental model

i.The machine in three parts

A coding agent is three things bolted together. The model predicts text and cannot touch anything — no files, no commands, no memory of yesterday. The harness is the program wrapped around it: opencode hands the model tools (read, edit, run), enforces permission gates, and feeds tool output back into the conversation. The loop is what makes it agentic: the model proposes an action, the harness executes it, the result feeds back in — until a stopping condition says halt. Remove the loop and you have a chatbot. A chatbot answers; an agent acts.

Two people on the same model through different harnesses get wildly different results — the harness is most of what you experience as "the product." And there is a second loop, the one you own, wrapped around the machine's: aim (one goal, one success test) → watch (skim before edits land) → verify (run the proof yourself) → commit (accept, correct, or restart clean). Every technique in this book lives somewhere in that chain.

One boundary before you touch anything. A workflow is ordinary code marching a model through steps a human already understands; an agent directs its own process, choosing tools as it goes. Agents trade predictability for flexibility and cost more in tokens and latency — so the field's most profitable bias is to start with the simplest thing that could work and reach for autonomy only when the task genuinely needs it. Say no to the agent when the steps are already known (a script is cheaper and cannot improvise), when you cannot state what "done" looks like (no finish line, no honest halt), when latency or cost budgets are tight (a loop of model calls is expensive by construction), or when mistakes are irreversible without a sandbox (live systems, other people's data). Autonomy amplifies whatever it touches, including mistakes.

ii.An honest word about speed · 3 min

Before the session, one uncomfortable measurement. In 2025 the independent nonprofit METR ran a randomized trial: experienced open-source developers, real issues in repos they knew, early-2025 tools. Read it in both directions — narrow setting, old tools, and METR itself now flags these results as out of date with newer data coming in. The durable lesson survives anyway:

+24%speedup developers predicted
+20%speedup they believed after
−19%measured reality · slower with AI

Nobody in that study sensed the slowdown. Your feeling of speed is not data — measure occasionally, and this book will keep asking you to. (Numbers re-verified 2026-09-03; METR's page now carries an "out of date" banner pointing at its 2026 follow-up.)

iii.The session · 35 min · opencode

Four steps. Each states its goal, gives you the exact thing to paste, shows what you should see, and tells you how to prove it. The transcript below is condensed from an actual run on 2026-09-03, not written for effect.

1.Make a scratch repo

Goal: a disposable repo with one file and one commit, so every later change is reviewable as a diff.

mkdir agent-first-run cd agent-first-run git init -q git config user.name "learner" git config user.email "learner@example.com"

Then create hello.js containing exactly one line — console.log('blank slate') — with your editor, and commit:

git add -A git commit -qm start

Terminal-only alternative (macOS, Linux, Git Bash): printf "console.log('blank slate')\n" > hello.js before the commit. Plain echo with quotes misbehaves on some Windows shells, so the editor route above is the default. The git config lines are one-time per machine — without them a fresh git commit refuses to run.

◆ ls → hello.js · ◆ git log --oneline → start One file, one commit. That is the entire setup.
✓ Verify
  • ls shows exactly hello.js
  • git log --oneline shows one commit

2.Launch opencode, paste one goal

Goal: one agent run with a falsifiable finish line. If you haven't installed opencode: npm install -g opencode-ai (needs Node.js — check with node --version; v24.13.0 used here, 2026-09-03), then opencode in the scratch repo. First launch walks through provider auth (/connect); the session below needs any working model.

Before you paste, write the stopping line down — on paper, in one sentence: hello() works via the node proof, no other files touched. That sentence is the stopping condition. The prompt below encodes it; writing it first is the habit, not the prompt.

In this repo, add a hello() function in hello.js that returns the string 'hello from my agent', and export it via module.exports. Then prove it works by running node to print require('./hello.js').hello(). Do not touch any other file.

Prefer non-interactive? The equivalent is opencode run -m <provider/model> "…" — same prompt, piped straight through. Prefer another harness? The prompt is portable: Claude Code, Codex CLI and Gemini CLI all accept it verbatim; only the launch command changes.

◆ opencode · read . → listing · read hello.js → 1 line ◆ opencode · edit hello.js → +6 −0 ◆ opencode · run proof → blank slate ↩ hello from my agent ✓ Condensed from a real run, 2026-09-03, model muse-spark-1.3, clean repo: only the two reads above, nothing else touched. Note the proof prints two lines — requiring the file also runs its top-level console.log. Read whole outputs, not last lines.
⚠ If stuck

Wrong files touched? First look: git status --short. Tracked modifications revert with git checkout .; brand-new files need git clean -fd <path> — checkout alone never removes untracked files. Then re-send the prompt with the last sentence standing alone on its own line. Constraints placed last are obeyed most.

✓ Verify
  • The session ended on its own after the proof passed (stopping condition met, not abandoned)
  • No new files appeared in the repo

3.Read the diff — out loud

Goal: prove you can explain every line the agent wrote. This is the line between agentic engineering and vibe coding: never commit what you can't explain.

diff --git a/hello.js b/hello.js · 1 file changed, 6 insertions(+)
console.log('blank slate')
+
+function hello() {
+ return 'hello from my agent';
+}
+
+module.exports = { hello };
✓ Verify
  • git diff --stat shows exactly 1 file, +6 −0
  • You can say what each added line does in one sentence

4.Run the proof yourself

Goal: replace trust with evidence. Plausible output is not correct output until your keystrokes say so.

node -e "console.log(require('./hello.js').hello())"
$ node -e "console.log(require('./hello.js').hello())" blank slate hello from my agent
✓ Verify
  • Output matches, produced by your terminal — the agent's proof and yours agree
Field note — The clean run read exactly two things (the directory, the one file) and touched one. An earlier run with a stray file in the folder read that too — agents read the workspace, not your intentions. Keep the repo clean, write the finish line before you start, and read whole outputs: the proof's first line (blank slate) was the file executing on import, a detail last-line skimming would miss.

Three failure modes will stalk every session from here, so learn their names now. The kitchen-sink session stuffs five goals into one thread until context rots and nobody can untangle the diff — fix: one goal per session, fresh starts are cheap. The trust-then-verify gap merges plausible output nobody read — fix: the verify ritual you just ran, never skipped. The infinite wander re-reads the same files forever — fix: timebox, narrow the goal, restart clean instead of nursing a doomed attempt. You now have the tools for all three. Session 02 puts them to work comparing harnesses: same task, four runners, one scorecard you fill in yourself.
