Patterns that ship

Name five workflow patterns, run the same task three ways with logged costs, and put your own work through a builder-critic gauntlet that names its biggest gap.

70 min · scratch repo · needs ch05 · verified 2026-09-03

Briefing · 5 min · shapes with prices

i.Five shapes, one baseline

Before the five named patterns, the zeroth option: one direct prompt, one session, a clear stopping condition. If that works — and it works far more often than beginners expect — you are done. Every pattern below is a purchase paid in tokens, latency, and parts that can disagree. The field's most profitable bias, from the people who named the patterns: start with the simplest thing that could work, and add complexity only when measurements say you must. The five names: prompt chaining (fixed substeps feeding forward — gather, draft, check), routing (classify first, dispatch to a specialist), parallelization (split independent pieces, or run candidates and vote), orchestrator-workers (a planner delegating to insulated workers), evaluator-optimizer (one model generates, another judges against criteria, loop until it passes — the only pattern that manufactures judgment where no test exists). §ii prices every shape; the session prices three of them with real runs.

Three companion disciplines ride with the patterns. Spec-driven development turns intent into the source of truth: constitution (non-negotiable principles) → specify (what and why, no tech choices) → plan (technical decisions grounded in the constitution) → tasks (ordered, checkable chunks) → implement → converge — with clarify, analyze, and checklist commands between the arrows, and the honest footnote that this is not waterfall (re-enter any step when reality argues back). Spec Kit's live 1.0.0 speaks two dialects you must both recognize: /speckit.* slash commands and speckit-* agent skills.

Tests as steering: red-green TDD in one line — write the failing test first, confirm it fails, then make it pass — because tests written after the code encode the model's own misreadings. Evals before iteration: where no assertion says "good enough," climb assertions → human/LLM judge → A/B, aligning any model-judge against 25–50 human labels first, because missing evals are the most common stall point in AI projects.

One honest boundary to close the briefing. The gauntlet you will run in step 5 — builder drafts, critic reviews blind-ish against criteria, binary verdict, biggest gap returns — is this book's house pattern, and it has no quantitative validation behind it. Its studied cousins are the evaluator-optimizer pattern above, Reflexion's reflection loop (peer-reviewed, but its 80→91% digits predate modern harnesses by years), and judge-alignment discipline. Presented as practitioner craft with the book itself as running evidence — which is exactly what "unvalidated" means here: try it, log it, keep it iff it works for you.

ii.What each shape costs · buy only with a reason

Price each shape before buying it, because the costs differ in kind, not just size. Named rules below are workshop rules — author's, ledger-backed where cited, disprovable where marked: log the disproof when you find one.

Chaining pays per handoff (tokens at every seam) and fails at the weakest stage — buy it when stages are genuinely distinct, not to make a two-step job look rigorous. A worked shape: changelog generation as gather (collect commits) → draft (write entries) → check (verify against the diff) — three genuinely different operations, each inspectable, each re-runnable alone when one fails. Routing buys focus for the price of a classifier you must maintain; it pays when inputs genuinely sort into kinds needing different handling — a triage bot sending bug reports, feature requests, and questions down three different prompts. Count the maintenance before you buy: labels drift as products change, new kinds arrive unannounced, and every misroute pays double (wrong handler plus recovery). A routing layer earns its keep with a fallback route — the explicit "none of the above" handler — and a confusion log you review monthly. Without both, the classifier silently becomes the system's most confident liar. Parallelization buys latency for coordination cost: sectioning pays on separable work (five independent file migrations), voting pays when disagreement is signal (three candidate fixes, tests as the ballot).

Orchestrator-workers buys scale for fragility, and deserves its warning label in full. Workers that cannot see each other compound misunderstandings: each worker's action carries implicit decisions the others never observe, retries collide on shared state, and the orchestrator merges debris it cannot attribute. The skeptics' documented position is that this fragility is structural, not a bug to prompt away — buy the pattern only with interfaces crisp enough to survive isolation (typed inputs, owned files, no shared mutable state) and a merge step you could defend in review. Concretely, an interface that survives isolation names three things per subtask: the exact files owned (no two workers share a write path), the exact shape returned (a schema, not prose), and the exact conflict rule (last-writer-wins per file, or orchestrator-mediated merge with the losing diff preserved in the log). Miss any of the three and the merge becomes archaeology. Evaluator-optimizer buys judgment for rounds: each loop costs a generation plus a judgment, and an unaligned judge optimizes noise loudly — align it against human labels first, exactly as the evals ladder demands, or the loop polishes confidently toward the wrong bar.

The separation of concerns inside spec-driven work is the whole design: specify owns what-and-why and explicitly excludes technology choices, plan owns the technical decisions grounded in the constitution, tasks makes the work ordered and checkable — and converge checks the implementation back against all three, appending leftovers as new tasks instead of declaring victory. Around the core sit the modifiers: clarify before planning, analyze for cross-artifact consistency after tasks, checklists that validate requirements like unit tests validate code, plus opt-in extensions for bug-fixing (assess → fix → test) and idea assessment (intake → decide). Install needs uv and Python — not installed on this machine by standing rule, so every Spec Kit claim here is docs-verified and reader-run, labeled as such. On evals mechanics: climb the ladder one rung at a time (assertion, then judge, then A/B), because each rung answers a different question — assertions check knowns, judges approximate taste, A/B measures outcomes — and skipping straight to judging means optimizing a bar nobody wrote down. Judge alignment itself is a protocol, not a hope: collect 25–50 human labels first, measure the model's agreement against them, iterate the judge prompt until agreement holds, and only then let it gate anything. An unaligned judge doesn't optimize quality; it optimizes noise, loudly — and the volume makes the failure hard to catch, because confident numbers look like rigor. The Reflexion export worth keeping is cheaper than its benchmark: between attempts, write down what failed and why instead of blindly retrying — a short post-mortem held where the next attempt can read it. Treat the digits as historical and the habit as current. And verify at every seam you paid extra to create: each handoff between stages multiplies unverified assumptions into the next stage's inputs, so by the time symptoms surface you can no longer attribute the failure. The chaining tax is not the tokens at the seams — it is the attribution debt. Check each stage's output against its input contract before passing it on, especially the seams that exist for ceremony rather than necessity.

Review the uncommitted diff against: (1) both tests genuinely pass (run them), (2) no other file touched, (3) no untested helper added. Verdict: SHIP or KILL plus the single biggest gap.

Read the table the way the doctrine demands: direct wins this task and should win most small tasks — the fancier shapes must beat 1x to justify themselves, and here neither does on cost. What they buy is not speed but different failure coverage: plan-first buys reviewability (the empty diff between runs is a decision point a second human could have entered), evaluator buys detection (the even-branch gap no test named). Chaining would buy inspectability here at a bad price — gather, draft, and check on a one-function fix is three seams for a two-step job — which is exactly how you learn the cost/kind distinction: name what each seam would have caught, and when the answer is "nothing," ship the boring version. Voting has one more failure mode worth knowing before you try it: correlated blindness. Candidates from the same model family share training and blind spots, so three votes can agree confidently on the same wrong answer — votes are signal only when the candidates genuinely disagree, which usually means different models or different decompositions, not three samples from one distribution. (Analysis, not measurement: disprove it by voting across families and logging when agreement misleads.) Your logbook extends this table to your tasks, and the day a shape's row beats direct on your work is the day you adopt it — with the measurement that proved it attached.

4.Red-green — the one-line prompt

Goal: the cheapest control surface in this book. Tests first, confirmed failure, then green — on a new function, so the suite grows instead of echoing.

This chapter's own lab demonstrates it: median.test.js was written before any fix and ran red on arrival (median-of-three failing, 1 pass 1 fail) — the confirmed failure this discipline demands. The confirmed failure is the point, and it protects against two distinct mistakes at once: code that doesn't work (the red you must turn green) and code nobody needs (dead code no test ever exercises can never turn a red test green, so it stands out immediately). Skip the confirmation and both protections evaporate — a test that passes before the fix is a participation trophy. Your turn, same shape:

Using red/green TDD: first write a failing test for even-length median (median([1,2,3,4]) === 2.5), confirm it fails, then implement until green. Do not touch any other file.
◆ red, verbatim from this chapter's lab: ✖ median of three · pass 1 · fail 1 Captured before any fix was written. Your red must look like this: named test, failing output quoted, implementation untouched.
✓ Verify
  • Red observed (failing output quoted) BEFORE any implementation edit
  • Green after; the critic's gap from step 3 is now covered by a test
  • Suite scanned for tests that never failed — unfailed tests are untested tests, name them
⚠ If stuck

Test passes before you implement? It cannot fail — rewrite it to assert the new behavior specifically (wrong values in, exact expected out). A test that passes on the old code is decoration.

5.Your gauntlet — blind-ish, binary, honest

Goal: run the book's engine on your own artifact. Builder drafts, critic judges against criteria you write down first, verdict is binary, biggest gap returns to builder. Exit on judgment, never on a round count.

Builder: draft [your artifact: a function, a config, a doc section]. Critic (fresh session): judge it against [your 3 written criteria]. Verdict SHIP or KILL + the single biggest gap. No scores.
◆ format reference, from the executed critic above: ◆ checklist 3/3 → verdict + "single biggest gap" named, no scores Not a second run — the shape of the first one, quoted so your critic's output has a template. Fresh session, criteria pasted, artifact attached.

Fresh session matters: the critic must not inherit the builder's rationalizations. New chat, criteria pasted in, artifact attached — empty transcript, clean eyes. Log rounds until the verdict flips or you stop the run; both outcomes teach. Set the exit rule before round one: the loop ends when the critic ships the work blind or when you stop it — this book's house rule is never to exit on a round count. And write the criteria narrowly enough to judge: "both tests pass" is checkable, "code is clean" is a mood. The critic can only manufacture the judgment your criteria describe, so vague criteria manufacture vague verdicts. Expect your first gauntlets to run long; the rounds get shorter as your builder learns what your critic checks. First gauntlet suggestion: run it on this chapter's own scorecard table — fresh session, criteria "numbers match the runs," verdict binary.
