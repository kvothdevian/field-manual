Map first, touch last

Hand an agent a shop you never wrote and walk out with a one-file fix: branch it, map it read-only, pin its behavior, and fence the edit before a single line changes.

75 min · scratch repo · needs ch06 · verified 2026-09-04

Briefing · 5 min · the map is the work

i.Brownfield in one paragraph

Brownfield means code you inherited: it runs, it earns, nobody remembers every decision inside it. You arrive with zero intuition and an agent that rewrites what it should reuse — one field report watched an agent build a duplicate email-service beside the existing one. So: three artifacts before any edit. A reversible baseline, a read-only neighborhood map, and a written blast-radius naming what may change, what must not, and which test proves it. No baseline, no map, no radius — no edit.

The arithmetic, illustrative rather than measured: no working context holds a whole repo, so every session is compression with judgment — sketch first, expand where the change lands, edit last. Aider's repo map is the canonical example: parse symbols, rank them by graph over file dependencies, pack the top under a token budget (default 1,000 tokens, verified live 2026-09-04). The budget buys visibility; what it cannot hold is blindness you chose. Name it in writing — "the map shows signatures, not timing" — and you hold the KNOW/MISS split of Fig. 11.

Then the arc: verify first, then explore, plan, implement, commit — the four-phase shape the Claude Code best-practices page prescribes, re-verified live 2026-09-04. Verification precedes exploration: hand the agent a runnable check so "looks done" is never the only signal. Exploration stays read-only; the plan names untouched files before changed ones; the timebox ends when the plan fits one breath. Ship the smallest change that satisfies it.

Two vocabularies keep the arc cheap. Refactoring moves: Fowler's catalog of behavior-preserving steps — rename, extract, move — each checked by the pinning test, never by taste. One move per session, never restructuring plus feature in one diff. Legibility: Ronacher's rule that agent-shaped code (local reasoning, grep-able names) steers better than rule lists, with Willison's field note concurring that agents mirror existing repo conventions, for good and ill. Point at the exemplar — "like that one" — not a style memo.

Specs on inherited ground: characterize current behavior first — Feathers' discipline of pinning what the code does today before judging it. Spec the delta, never the system: the Existing Projects guide on the Spec Kit repo (verified live 2026-09-04) starts from a reviewable baseline, captures guardrails already true, and scopes the first change to one slice. One enterprise case study argues ~80% per-phase accuracy compounds to 0.8⁵ ≈ 0.33, justifying gates every phase — a single-project sample, suggestive not proven. Boundary: maps rank symbols, not coupling, so pair every map with a runtime check.

ii.What the agent actually sees · budgets buy visibility

Walk the funnel left to right and each stage has exactly one job. Parsing turns files into symbols: class names, function signatures, the lines that define them. Ranking scores those symbols by how much of the codebase references them, so entry points and hubs float up and leaf utilities sink. Packing fills the token budget top-down and stops — everything below the line is the MISS list, and the MISS list is a deliverable, not an apology. A map that cost 1,000 tokens and names its blindness beats a 50,000-token dump nobody can audit, because the small map can be read, challenged, and re-run.

The MISS row is where coupling hides. The map says the duplicate exists; only the test run says whether production touches it. That is the standing rule for this chapter: a symbol map is never a behavior proof. Every claim the map suggests — "the duplicate is dead," "the rate flows from rates.js" — gets a runtime check before any edit, and the check is the pinning test of step 3.

iii.Fences before edits · the blast-radius plan

The blast-radius is a written plan with three lanes, approved before the agent may write. Read-only lanes hold files the agent may open but never modify; the planned lane holds the one file it may change; the pinning test holds the behavior that must stay green. Untouched files are walled off by name — shape plus label, never a vague "don't break anything." The table below is the actual plan from the executed session, and step 4 pastes it verbatim.

Two vocabularies keep the fenced edit small. Refactoring moves stay mechanical: this session's fix is a constant-substitution, the smallest move in Fowler's catalog, verifiable line by line. Legibility does the steering the rules cannot: the fixed line reads its rate from the hub module the way the discount already does, so the file converges on one exemplar pattern — every rate comes from rates.js — instead of obeying a comment. When the next session maps this repo, the map shows one truth table and zero suspects, because the fix deleted a suspicion rather than adding a rule.

iv.Specs on inherited ground · characterize, then delta

Feathers' order of operations is invariant first, judgment second: write the test that captures what the system does today, watch it pass, and only then decide whether today's behavior is correct. The legacy-cart test that asserts the duplicate still computes 7% looks strange — why pin a bug? — until the surgical edit lands: the pinned duplicate proves the fix went to the live path, because a fix routed through the duplicate would have moved the pinned number. Characterization tests are documentation that bites back.

pin (shop.test.js, unchanged by the fix) + surgical diff (shop.js, the only file touched)
assert.equal(legacyCartTotal([{ price: 25, qty: 2 }]), 53.5); // stale 7% pinned
@@ shop.js — 2 insertions, 2 deletions, every line explained @@
-const { DISCOUNT_THRESHOLD, DISCOUNT_RATE } = require("./rates");
+const { DISCOUNT_THRESHOLD, DISCOUNT_RATE, TAX_RATE } = require("./rates"); // line 1: import the truth
- const taxed = (subtotal - discount) * 1.07;
+ const taxed = (subtotal - discount) * (1 + TAX_RATE); // line 12: read the rate, stop hard-coding
proof: node --test shop.test.js → 3 pass, 0 fail (executed 2026-09-04)

The spec for the delta reads as a change request, not a system overview: "cartTotal follows rates.js; legacyCartTotal stays untouched." The Existing Projects guide's brownfield loop — baseline, guardrails, one bounded slice, plan against the repo — is exactly steps 1–4 below, and the community's loudest request (a first-party brownfield bootstrap, spec-kit issue 1436) is lead-only signal, never cited as fact: it tells you where teams feel friction, not what the tool guarantees. Where this breaks down: specs describe intended deltas, maps describe static symbols, and neither describes runtime coupling — the pinning test is the third leg, and a session missing any one of the three is guessing.

v.Session — the inherited shop · executed 2026-09-04

Three files, plain node --test, zero installs. The shop arrives broken the way inherited code is broken: a live total that hard-codes last year's 7% tax, a truth table that already says 9%, and a stale duplicate waiting to absorb your fix. 1.Branch before you brief

Goal: a reversible baseline. Commit the inheritance untouched, open an agent-fix branch, verify the tree is clean — reversibility before comprehension.

git init; git add -A; git commit -m "baseline: inherited shop before mapping"; git checkout -b agent-fix; git status

✓ Verify

⚠ If stuck

Branch already exists from a previous attempt? Delete it (git branch -D agent-fix) and re-cut from the baseline — a stale branch is an unprotected checkout wearing a costume.

4.Surgical edit in a written blast-radius

Goal: state the plan (touch / NOT-touch / pinning test), approve it, then land a 1-file diff with every line explained and the suite green.

BLAST RADIUS (approved): TOUCH shop.js cartTotal only — replace hard-coded 1.07 with (1 + TAX_RATE) imported from ./rates.js. NOT-TOUCH: rates.js, shop.test.js, legacyCartTotal. PINNING TEST: cartTotal follows the rates.js truth table (9 percent tax). Make the edit, then run node --test shop.test.js and report.
◆ surgical · shop.js | 4 ++-- · 1 file changed, 2 insertions(+), 2 deletions(-) ◆ proof · tests 3 · pass 3 · fail 0 ✓ Executed 2026-09-04 via opencode run. Line 1 imports the truth; line 12 reads it. Every other line of the repo is byte-identical — that is what "surgical" means here.
✓ Verify
  • git diff --stat shows exactly 1 file; each changed line explained; suite green from your own terminal run
⚠ If stuck

Diff touches 2+ files? Revert and re-paste the NOT-TOUCH list — the plan failed, not the fix. A second file in the diff is a second review you never scheduled.

5.Break it on purpose (optional, reader-run)

Goal: feel what the map saved you. Apply the same rate change through the duplicate instead, watch the pinning test stay red, then revert — contrast as teacher.

Revert to the baseline commit. Now fix ONLY legacyCartTotal to use TAX_RATE (leave cartTotal hard-coded). Run node --test shop.test.js and report. Then revert again.
◆ contrast (expected) · duplicate fixed · pinning test still red — 53.5 !== 54.5 Reference expectation, not an executed run: the pinning test watches the live path, so a duplicate-only fix changes the suite's output nowhere. Revert when done — the branch must end green.

⚠ If stuck

Lost track of which state you're in? git stash then git diff --stat — empty means you're at baseline, one file means you're mid-contrast. Name the state before the next command.
